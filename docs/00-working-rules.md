# 작업 운영 규칙

## 목적

집신의 기획·개발 과정에서 대화와 결정이 사라지거나 담당자가 바뀌어도 맥락이 끊기지 않도록 모든 작업을 문서와 Git 이력으로 남긴다.

## 표준 작업 순서

1. **계획 보고:** 작업을 시작하기 전에 수행 순서를 사용자에게 알린다.
2. **기존 상태 확인:** 관련 문서, 코드, 결정과 미완료 항목을 확인한다.
3. **작업 수행:** 요청된 기획·디자인·개발 작업을 진행한다.
4. **문서 반영:** 요구사항, 결정과 변경 내용을 관련 문서에 기록한다.
5. **대화 저장:** 대화가 한 페이지 이상 길어지거나 중요한 제품 판단이 나오면 날짜별 대화 기록을 만든다.
6. **검증:** 문서 링크, 코드 실행, 화면 또는 기능을 작업 성격에 맞게 확인한다.
7. **결과 보고:** 완료한 내용, 확인 결과, 미결정 사항과 다음 작업을 정리한다.
8. **Git 저장:** 변경사항을 커밋하고 원격 저장소가 연결되어 있으면 GitHub에 푸시한다.

## 문서 구분

| 위치 | 용도 |
|---|---|
| `docs/` | 현재 유효한 제품기획과 설계 |
| `docs/decisions/` | 중요한 선택의 이유와 영향 |
| `docs/conversations/` | 날짜별 대화와 발견 내용 |
| `docs/worklogs/` | 실제 수행한 작업과 검증 결과 |

## 상태 표기

- **확정:** 현재 제품 기준으로 사용
- **가설:** 실제 사용자 또는 결제로 검증 필요
- **미결정:** 사용자 판단 또는 추가 조사가 필요
- **후속:** MVP 이후 검토

## Git 저장 원칙

- 비밀번호, 인증번호, 개인 연락처, 실제 계좌번호와 원본 계약서는 커밋하지 않는다.
- 예시 자료는 개인정보를 제거하거나 가상 데이터로 바꾼다.
- 기획과 코드가 달라지지 않도록 기능 변경 커밋에는 관련 문서 변경도 포함한다.
