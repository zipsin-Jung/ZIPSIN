## 3. 서비스의 현재 정의

집신은 단순 수리 중개 서비스가 아닙니다.

> 계약 전부터 입주·거주·수리·관리·퇴거까지 흩어진 기록을 집 한 채 기준으로 연결하는 서비스

핵심 메시지:

> 사람이 바뀌어도, 집의 기록은 남습니다.

공인중개사무소는 초기 결제 고객이자 도입 채널이지만 제품의 유일한 주인은 아닙니다. 대표 공인중개사, 보조원, 임대인, 임차인이 실제 역할이며, 수리기사는 특정 집의 특정 수리 업무에 기간 한정으로 참여하는 관계자입니다.

기록은 개인 직원이 아니라 집·계약·사무소 업무에 연결합니다. 집의 장기 이력은 이어질 수 있지만 이전 계약자의 이름, 연락처, 대화, 계약서, 생활 사진 같은 개인정보는 다음 계약에 자동으로 이어지지 않습니다.

## 4. 공개 홈페이지와 로그인 후 홈을 혼동하지 마세요

### 공개 홈페이지 `/`

목적은 처음 방문한 사람이 집신이 무엇인지 이해하도록 하는 것입니다.

- 오른쪽 상단에 `로그인`과 `회원가입`을 항상 표시해야 합니다.
- `로그인`은 `/login`, `회원가입`은 `/signup`으로 연결합니다.
- 현재 코드의 `components/Header.tsx`에는 아직 `사전 회원 가입 하기`만 있어 이 요구가 반영되지 않았습니다.
- 홈페이지에서는 왜 필요한지 실제 사례로 설명합니다.
- 개인 사용자의 실제 일정은 보여주지 않습니다. 제품 미리보기를 쓰더라도 하나의 일관된 가상 사례만 사용합니다.
- 기존 문구 `사람이 바뀌어도, 집의 기록은 남습니다.`는 사용자가 마음에 들어 했습니다.
- 초보자가 만든 템플릿처럼 보이지 않게 밝고 신뢰감 높으며 고급스럽게 구성합니다.
- 로고는 초록 지붕·금색 창문·금색 무한대의 실제 집신 로고를 사용합니다.
- 캐릭터는 보조 안내자이며 화면을 지배하거나 버튼을 가리면 안 됩니다.

홈페이지에서 설명할 결제 이유의 실제 사례:

1. 보일러 재고장: 이전 업체·부품·사진·비용을 바로 확인
2. 입주·퇴거 상태 차이: 입주 전후 사진과 요청 시점을 같은 흐름에서 확인
3. 담당자 변경: 개인 카카오톡이 아니라 집에 남은 일정과 다음 행동을 인계
4. 수리기사 방문: 해당 수리에 필요한 사진과 일정만 기간 한정으로 공유
5. 다음 계약 준비: 개인정보를 제외한 집 이력과 증빙을 보고서로 정리

### 로그인 후 홈 `/home`

목적은 가입 사용자가 매일 확인할 다음 행동을 바로 보여주는 것입니다.

첫 아하 모먼트:

> 내가 놓치면 안 되는 우리 집의 다음 일이 바로 보인다.

첫 설계 기준은 `집 한 채를 가진 일반 사용자`입니다.

- 선택한 집의 현재 관계는 자가·전세·월세 중 실제 상태 하나만 표시합니다.
- 가장 가까운 중요 일정 하나를 가장 크게 보여줍니다.
- 그 일정에 연결된 지금 해야 할 행동을 보여줍니다.
- 수리 이력, 사진, 비용, 참여자는 행동의 근거로 연결합니다.
- 예시: `전세 거주 중` → `전세 만기 D-38` → `임대인에게 갱신 의사 전달` → 입주 사진·계약 기록 확인.
- 여러 집을 가진 임대인·중개사 화면에서는 집마다 가장 가까운 일정 하나씩 별도 카드로 보여줍니다.
- 한 집에 매매 잔금·전세 만기·월세 납부를 동시에 표시하지 마세요.

현재 `app/(app)/home/page.tsx`는 `첫 집 등록 준비 중`이라는 빈 화면 뼈대만 있습니다. 중요 일정 홈은 아직 구현되지 않았습니다.

## 6. 집 키 방향

등기부등본은 집 단위로 이력이 이어진다는 설명을 위한 비유일 뿐입니다. 집신을 `온라인 등기부`, `공식 집 이력`, `소유권 증명`, `검증된 사실`처럼 표현하지 마세요.

집 키 권장 정의:

- 주소는 집 후보를 찾는 시작점으로만 사용합니다.
- 주소만으로 비공개 기록 또는 기록 존재 여부를 공개하지 않습니다.
- 집 키는 영구 마스터 비밀번호가 아닙니다.
- 집 키는 역할·범위·기간이 지정된 일회성 또는 단기 초대권입니다.
- 로그인과 관계 확인 후 실제 멤버십을 만들고, 키 자체로 계속 접근하지 않습니다.
- 계약 종료, 직원 퇴사, 수리 완료 시 접근을 종료합니다.
- 수리기사는 특정 수리 사건의 주소·방문 일정·필요 사진·완료 기록만 봅니다.
- 공인중개사와 보조원은 배정된 현재 계약·업무만 봅니다.
- 장기 집 이력에는 개인정보를 제거하고 승인된 요약만 남깁니다.

기술적으로는 주소, 불변 집 ID, 초대 토큰, 실제 관계 멤버십을 분리해야 합니다. 집 키 원문은 생성 시 한 번만 보이고 DB에는 안전한 파생값만 저장해야 합니다. 모든 권한은 서버와 RLS에서 검증해야 합니다.

집 키는 아직 사용자 최종 승인을 받은 정책이 아닙니다. 구현하지 말고 먼저 아래 미결정 사항을 한 번에 하나씩 사용자에게 쉽게 설명해 결정받으세요.

1. 집 키 없는 주소 검색자에게 공개정보를 어디까지 보여줄지
2. 최초 집 관리자 연결을 누가 어떤 근거로 확인할지
3. 장기 집 이력으로 올릴 수 있는 기록과 승인 주체
4. 계약 종료 후 임차인의 열람·내보내기 기간

권장 기본값은 `주소와 건물 구분 같은 공개 기본정보만 표시하고, 집신 등록 여부·기록 존재·관계자·사진·일정·비용은 모두 숨김`입니다.

## 8. 이미 구현된 인증 기능

기술 스택은 실제 Next.js App Router, TypeScript, Tailwind CSS, Supabase입니다.

구현된 경로:

- `/login`: Google·카카오·네이버 간편 로그인 진입 + 아이디·비밀번호 로그인
- `/signup`: 아이디·비밀번호·이메일 회원가입
- `/signup/verify`: 휴대전화 인증·이름·동의
- `/account-recovery`: 가입 이메일로 계정 복구 요청
- `/reset-password`: 아이디 확인·새 비밀번호 설정
- `/onboarding/role`: 대표 공인중개사·보조원·임대인·임차인 역할 선택
- `/home`: 보호된 빈 홈 뼈대
- `/auth/callback`: 인증 콜백

구현된 보안:

- 비공개 `account_usernames` 아이디 매핑
- 아이디 4~20자 영문 소문자·숫자·밑줄
- DB 고유 제약으로 동시 중복 방지
- 아이디 로그인 시 이메일을 화면·응답에 노출하지 않음
- 같은 이메일만으로 소셜과 일반 계정을 자동 병합하지 않음
- 로그인·가입·복구에 DB 원자 요청 제한
- 제한 키는 32자 이상 서버 비밀값으로 HMAC 처리
- 가입 보상 삭제 실패 시 비공개 `auth_cleanup_queue` 기록
- 대기열 기록도 실패하면 오류 원문 없이 구조화 서버 경보
- 외부·프로토콜 상대·역슬래시 변형 복귀 경로 차단
- 아이디 로그인 기능 플래그 롤백 가능

주요 migration:

- `supabase/migrations/202610020001_auth_profile.sql`
- `supabase/migrations/202610060001_account_usernames.sql`

주의:

- 2026-10-02 인증 기반 migration은 Supabase Preview에 적용됐습니다.
- 2026-10-06 아이디·요청제한 migration은 로컬에만 있고 Preview에는 아직 적용되지 않았습니다.
- `AUTH_RATE_LIMIT_HMAC_SECRET`도 Preview Vercel 환경변수에 아직 추가되지 않았습니다.
- 실제 이메일 확인·복구 왕복은 미검증입니다.
- Google·카카오·네이버 실제 OAuth 왕복은 미검증입니다.
- Naver는 Supabase 기본 제공자로 단정하지 말고 기존 `DEC-011`의 Custom OAuth2 방향을 확인하세요.

## 11. 사용자 작업 방식과 절대 규칙

- 모든 작업 전에 수행 순서를 먼저 보고합니다.
- 한국어 존댓말로 짧고 쉽게 설명합니다.
- 사용자는 개발 초보자이므로 기술적 사소한 선택을 반복해서 묻지 말고 합리적인 기본값을 제안합니다.
- 기획과 설계는 구분합니다.
- 흐름은 `기획 → 설계 → 개발 → 테스트 → 수정 → 완료보고 → 사용자 승인`입니다.
- 큰 기능의 첫 작업은 총괄비서·기획디자인·설계개발·품질비판 네 역할 회의로 시작합니다.
- 한 페이지 이상 길어진 제품 대화는 `docs/conversations/`에 저장합니다.
- 작업 후 `docs/worklogs/`에 순서·변경·검증·남은 일을 저장합니다.
- 제품 방향 결정은 `docs/decisions/`에 새 기록으로 남기며 과거 기록을 덮어쓰지 않습니다.
- 변경 문서는 `/Users/zipsin/Desktop/코덱스랑/집신/`에도 같은 구조로 복사합니다.
- 개인정보, 전화번호, 계좌번호, 인증키, 실제 계약서 원본은 Git에 저장하지 않습니다.
- 기존 사용자 파일과 코드를 삭제하지 않습니다. 복구 불가능한 삭제를 하지 않습니다.
- 전체 파일을 대화에 재출력하지 않습니다.
- 분명한 필요가 없는 기능 추가·도구 설치·대규모 리팩터링을 하지 않습니다.
- 실제 접수·실결제·외부 로그인 왕복을 검증하지 않았다면 완료했다고 말하지 않습니다.
- GitHub 푸시, Supabase migration, Vercel Preview/Production 배포는 사용자에게 마지막 변경 내용과 검증 결과를 보고하고 별도 승인을 받은 뒤 진행합니다.
- Production 공개는 Preview 검수와 별도의 최종 승인 대상입니다.
