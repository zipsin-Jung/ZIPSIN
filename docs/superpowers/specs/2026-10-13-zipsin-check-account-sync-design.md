# 집신체크 단일계정·후보기록 이전 제품·UX·기술 설계

- 작성일: 2026-10-13
- 상태: 서면 명세 사용자 검토 대기
- 선행 승인: 2026-10-13 여섯 역할 최초회의 방향 승인
- 관련 결정: `DEC-011`, `DEC-013`, `DEC-014`, `DEC-017`, `DEC-019`
- 구현 기준: 실제 Next.js App Router 서버 런타임, Supabase Auth·Postgres·비공개 Storage

## 1. 목적과 성공 기준

집을 알아보는 사용자가 집신체크를 로그인 없이 사용한 뒤, 장기 보관과 다른 기기 복원을 원할 때 집신 계정 하나로 가입하거나 로그인해 임차인 사용자로 유입되게 한다. 사용자가 직접 고른 후보집 자료만 본인 비공개 초안으로 옮기며, 역할·주소·유입 출처만으로 특정 집·계약·사무소 권한을 만들지 않는다.

배포 전 성공 기준은 다음과 같다.

1. 비회원 체크·메모·사진·비교가 가입 없이 계속 동작한다.
2. 신규·기존 사용자가 집신 단일 세션으로 인증하고 중단한 이전을 재개한다.
3. 후보·필드·사진을 사전검토하고 명시적으로 동의한 자료만 서버에 저장한다.
4. 서버 후보는 계정 소유자만 읽고 수정·삭제할 수 있다.
5. 인증 취소, 세션 만료, 네트워크 중단, 중복 제출과 사진 부분 실패에도 로컬 원본과 재시도 경로가 남는다.
6. Preview 전 자동검사와 실제 브라우저 검수에서 P0·P1 0건, 선언한 제품 코드 네 커버리지 지표 각각 80% 이상을 만족한다.

## 2. 사실·가정·정책 경계

### 확인된 사실

- 현재 `/ck`는 `zipsin-check:v2` localStorage와 IndexedDB 사진 저장소를 사용한다.
- 현재 집신 앱에는 실제 계정·DB·서버 파일 저장 기능이 없다.
- 집신체크는 집신 단일 계정의 서브서비스이며 별도 계정을 만들지 않는다.
- 사용자가 직접 저장을 선택하기 전에는 가입 화면을 자동으로 띄우지 않는다.

### 이번 명세의 가정

- 최초 실제 수직 흐름을 집신체크 유입과 본인 후보집 저장으로 제한한다.
- 운영 공급자 키가 없어도 테스트 어댑터로 자동검사할 수 있고, Production에서 테스트 인증은 실행되지 않는다.
- 서버 이전 성공 뒤에도 로컬 원본은 자동 삭제하지 않는다. 사용자가 별도 행동으로 삭제한다.

### 운영 전 별도 정책 승인

- 개인정보의 확정 보존기간과 탈퇴 후 법적 보관 범위
- 실제 휴대전화 인증 업체와 횟수·비용 정책
- Naver Custom OAuth 운영 활성화
- 운영 도메인, OAuth callback과 Production 환경값

위 항목이 미확정이어도 배포 전 코드는 본인 전용 후보 삭제 기능과 공급자 비활성 상태로 안전하게 준비할 수 있다. 다만 실제 운영 배포는 승인하지 않는다.

## 3. 범위

### MVP 포함

- 기존·신규 집신 계정 로그인 진입과 세션 복구
- Google·Kakao OAuth 어댑터, Naver Custom OAuth 준비 상태
- 집신체크 유입 출처와 `집 구하는 중/임차인` 사용자 유형 확인
- 후보 1~3채, 포함 필드와 사진의 이전 미리보기·동의
- 본인 전용 후보집 초안, 답·메모·사진 저장
- 중복 방지, 부분 실패, 재시도와 다른 브라우저 복원
- 서버 후보 삭제, 로컬 원본 별도 삭제
- DB migration, RLS, Storage 정책, 환경값 예시와 롤백 문서
- Preview 전 테스트·브라우저·독립 검수 자료

### 명시적 제외

- Production 배포, DNS 변경과 운영 OAuth 활성화
- 주소로 기존 집·사무소·임대인 기록 검색 또는 자동 연결
- 계약 관계 생성과 임차인의 실제 계약 공간 접근
- 입주·거주·퇴거 기록 자동 전환
- 사무소·임대인 공유, 공개 리뷰와 마케팅 자동 동의
- 실제 결제, 문자 발송과 운영 휴대전화 인증

## 4. 요구사항과 수락기준

### ZCA-001 비회원 사용 연속성

- 역할: 로그인하지 않은 집신체크 사용자
- 트리거: `/ck` 진입 또는 가입 흐름 취소·실패 후 복귀
- 주 흐름: 등록 → 현장 5개 → 메모·사진 → 비교 → 필요할 때 저장 선택
- 상태: 신규, 기존 로컬 기록, 오프라인, 저장소 손상, 가입 취소 복귀
- AC-001-A: 가입 없이 등록·체크·요약·2~3채 비교를 완료할 수 있다.
- AC-001-B: 로그인·가입 취소 또는 실패 후 후보, 답, 메모, 사진과 비교 선택이 유지된다.
- AC-001-C: 계정 저장을 선택하지 않은 사용자에게 가입 모달을 자동 표시하지 않는다.

### ZCA-002 집신 단일 계정

- 역할: 신규 또는 기존 집신 사용자
- 트리거: `집신에 저장하기`
- 주 흐름: 안전한 복귀 경로 저장 → 로그인·가입 → 세션 확인 → 이전 재개
- 상태: 제공자 선택, 이동 중, 성공, 취소, 오류, 세션 만료, 이미 가입된 계정
- AC-002-A: 집신체크 전용 계정이나 별도 비밀번호를 만들지 않는다.
- AC-002-B: OAuth 완료 후 서버가 세션을 확인하기 전에는 로그인·이전 성공으로 표시하지 않는다.
- AC-002-C: 같은 이메일만으로 서로 다른 소셜 ID를 자동 병합하지 않는다.
- AC-002-D: 외부 URL과 허용하지 않은 경로를 복귀 주소로 사용하지 않는다.

### ZCA-003 임차인 유입 확인

- 역할: 집신체크에서 인증한 사용자
- 트리거: 인증 완료 후 최초 유입 확인
- 주 흐름: `집 구하는 중/임차인` 제안 → 설명 확인 → 사용자가 확인·변경 → 저장
- 상태: 미확인, 제안, 변경, 저장 중, 오류, 완료
- AC-003-A: `signup_source=zipsin_check`와 사용자가 확인한 사용자 유형을 분리 저장한다.
- AC-003-B: 제안값은 사용자가 변경할 수 있다.
- AC-003-C: 유입 출처·사용자 유형 저장만으로 집·계약·사무소 관계를 생성하지 않는다.

### ZCA-004 이전 사전검토와 동의

- 역할: 인증된 집신체크 사용자
- 트리거: 계정 저장 재개
- 주 흐름: 후보 1~3채 선택 → 필드·사진 확인 → 민감정보 안내 → 이전 동의
- 상태: 후보 없음, 기본 1채, 2~3채, 사진 없음, 민감정보 경고, 동의 전, 유효성 오류
- AC-004-A: 기본 선택은 사용자가 CTA를 누른 현재 후보 한 채다.
- AC-004-B: 후보별 별칭, 위치·조건, 담당자 연락처, 현장 5개, 메모와 사진 개수를 보여준다.
- AC-004-C: 후보 전체를 제외할 수 있고 사진은 개별 포함·제외할 수 있다.
- AC-004-D: `나만 봄`, 저장 목적, 옮기는 자료와 옮기지 않는 자료를 표시한다.
- AC-004-E: 기록 이전 동의와 마케팅 동의를 결합하지 않는다.

### ZCA-005 안전하고 중복 없는 이전

- 역할: 인증·동의를 완료한 사용자
- 트리거: `선택한 기록 저장`
- 주 흐름: manifest 생성 → 텍스트 저장 → 사진 업로드 → 서버 검증 → 결과 확정
- 상태: 준비, 텍스트 저장, 사진 업로드, 검증, 성공, 부분 성공, 실패, 재시도
- AC-005-A: 후보는 계정 소유자만 보는 비공개 `candidate_draft`로 생성한다.
- AC-005-B: 이전 요청 ID와 로컬 후보 ID의 사용자별 고유 제약으로 재요청 중복을 막는다.
- AC-005-C: 서버가 확정 응답하기 전 로컬 텍스트·사진을 삭제하지 않는다.
- AC-005-D: 사무소·임대인·다른 사용자와 자동 공유하지 않는다.
- AC-005-E: 클라이언트가 보낸 user ID를 신뢰하지 않고 서버 세션의 사용자 ID를 사용한다.

### ZCA-006 검증과 다른 기기 복원

- 역할: 이전을 완료한 사용자
- 트리거: 결과 화면 또는 다른 브라우저 로그인
- 주 흐름: 저장 후보·항목·사진 수 확인 → 내 후보집 목록·상세 조회
- 상태: 전체 성공, 부분 성공, 빈 목록, 목록, 상세, 세션 만료, 불러오기 오류
- AC-006-A: 서버가 확인한 후보 수, 사진 수와 누락 항목을 결과에 표시한다.
- AC-006-B: 다른 브라우저 로그인 후 같은 후보 답·메모·사진을 본다.
- AC-006-C: 데이터 없음과 권한 거부를 같은 빈 화면으로 숨기지 않는다.

### ZCA-007 취소·실패·재시도

- 역할: 인증 또는 이전 중인 사용자
- 트리거: 취소, 공급자 오류, 오프라인, 세션 만료, 용량 오류, 사진 일부 실패
- 상태: 취소, 재로그인 필요, 재시도 가능, 일부 성공, 재시도 중, 복구 불가
- AC-007-A: 실패 원인과 성공·실패 항목을 구분하고 전체 성공으로 표시하지 않는다.
- AC-007-B: 실패한 항목만 같은 이전 요청 ID로 재시도할 수 있다.
- AC-007-C: 부분 성공 뒤 페이지를 닫아도 서버 manifest와 로컬 연결 정보로 복구한다.
- AC-007-D: 인증 취소 시 원래 `/ck` 화면으로 돌아가며 로컬 기록이 남았음을 알린다.

### ZCA-008 후보 초안과 장기 집 이력 분리

- 역할: 후보집을 저장한 사용자
- 트리거: 후보 상세 또는 `이 집으로 결정`
- 상태: 개인 후보, 전환 안내, 관계 확인 필요
- AC-008-A: 후보 초안에는 장기 `home`, `contract`, `membership` 관계를 자동 생성하지 않는다.
- AC-008-B: 동일 주소의 기존 집·계약·이전 사용자 자료를 조회하거나 병합하지 않는다.
- AC-008-C: `이 집으로 결정`은 후속 기능임을 안내하고 자동 전환하지 않는다.

### ZCA-009 삭제와 로컬 원본

- 역할: 후보집 소유자
- 트리거: 내 후보집 또는 `/ck`의 저장 결과
- 상태: 서버 삭제 확인, 삭제 중, 성공, 실패, 로컬 유지, 로컬 별도 삭제
- AC-009-A: 서버 후보 삭제와 현재 브라우저 로컬 삭제를 서로 다른 행동으로 표시한다.
- AC-009-B: 서버 삭제는 후보 텍스트와 연결 사진을 대상으로 하며 다른 후보에 영향을 주지 않는다.
- AC-009-C: 삭제 실패 시 남은 범위와 재시도 방법을 표시한다.
- AC-009-D: 다른 사용자의 후보 ID로 삭제 요청하면 존재 여부를 노출하지 않고 거부한다.

## 5. 사용자 흐름

### FLOW-ZCA-01 신규 회원

`CK 결과/비교 → 저장 미리보기 → 집신 로그인·가입 → 임차인 유형 확인 → 이전 동의 → 이전 진행 → 검증 결과 → 내 후보집`

### FLOW-ZCA-02 기존 회원

`CK 결과/비교 → 로그인 → 인증 전 선택 복원 → 이전 미리보기 → 동의 → 이전 → 내 후보집`

### FLOW-ZCA-03 취소·인증 실패

`OAuth 취소/오류 → 안전한 /ck 복귀 → 동일 후보·비교 선택 → 로컬 유지 안내 → 재시도 또는 나중에`

### FLOW-ZCA-04 부분 실패

`텍스트 저장 성공 → 일부 사진 실패 → 성공/실패 구분 → 로컬 유지 → 실패 사진만 재시도 → 서버 재검증`

### FLOW-ZCA-05 다른 기기 복원

`다른 브라우저 로그인 → 세션·온보딩 확인 → 내 후보집 → 목록·상세·사진`

### FLOW-ZCA-06 삭제

`내 후보집 상세 → 서버 후보 삭제 확인 → 텍스트·사진 삭제 결과 → 로컬 원본 별도 선택`

- 한 화면의 주요 행동은 하나로 하고 `나중에`를 숨기지 않는다.
- `가입하지 않으면 기록이 사라진다`는 압박 문구를 쓰지 않는다.
- 이전 화면에 `현재는 나만 볼 수 있어요`를 고정 표시한다.
- 진행 단계는 색상만이 아니라 문구와 `aria-live`로 알린다.
- 오류는 원인, 보존된 자료, 다음 행동을 함께 설명하고 첫 오류로 포커스를 이동한다.
- 320px, 390px, 1440px, 키보드, 스크린리더와 200% 확대를 지원한다.

## 8. 인증·인가·Storage

- Next.js `output: export`를 제거하고 App Router 서버 런타임과 `@supabase/ssr` 쿠키 세션을 사용한다.
- Google·Kakao는 Supabase 기본 OAuth, Naver는 Custom OAuth 설정 여부에 따라 활성화한다.
- callback은 PKCE code 교환 뒤 내부 허용 경로만 사용한다.
- 테스트 인증·전화 공급자는 Production에서 시작할 수 없게 환경 검사를 둔다.
- 모든 Server Action·Route Handler는 쿠키 세션에서 사용자 ID를 구하고 요청 body의 owner ID를 무시한다.
- Postgres RLS는 `owner_user_id = auth.uid()`인 후보·manifest만 select/insert/update/delete 허용한다.
- 사진 bucket은 비공개이고 경로를 `{auth.uid()}/{candidateId}/{photoId}`로 제한한다.
- 사진 열람은 서버 권한 확인 뒤 짧은 만료시간의 서명 URL을 발급한다.
- 서비스 역할 키는 브라우저 번들·Git·로그에 넣지 않는다.

## 9. API와 이전 프로토콜

### 서버 인터페이스

- `startOAuth(provider, returnTo)` — 공급자 설정과 안전한 복귀 경로 확인
- `getTransferPreview(localManifest)` — 서버 전송 전 클라이언트 형식 검증
- `createTransferManifest(input)` — 세션 사용자 기준 manifest 생성·재사용
- `upsertCandidateDraft(manifestId, candidate)` — 사용자별 로컬 후보 ID로 멱등 저장
- `uploadCandidatePhoto(manifestId, candidateId, itemId, photo)` — 형식·크기·소유권 확인 뒤 비공개 업로드
- `finalizeTransfer(manifestId)` — DB·Storage 실제 개수와 예상 개수 비교
- `retryTransferItems(manifestId, itemKeys)` — 실패 항목만 재시도
- `listCandidateDrafts()` / `getCandidateDraft(id)` — 본인 후보 조회
- `deleteCandidateDraft(id)` — 소유권 확인 후 DB·사진 삭제 결과 반환

### 이전 순서

1. 클라이언트가 v2 후보와 사진을 읽고 민감정보 경고를 실행한다.
2. 사용자가 후보·필드·사진을 선택하고 이전 동의한다.
3. 서버는 세션, 입력 크기와 schema를 검사하고 manifest를 생성하거나 기존 것을 돌려준다.
4. 후보 텍스트를 upsert하고 항목별 결과를 manifest에 기록한다.
5. 사진을 한 장씩 업로드하며 성공·실패를 별도로 기록한다.
6. finalize가 예상·확정 개수를 비교해 전체·부분·실패를 결정한다.
7. 성공 뒤에도 로컬 원본은 유지하고 사용자가 선택할 때만 별도 삭제한다.

## 10. 실패·복구·롤백

- OAuth 취소: `/ck?auth=cancelled` 같은 허용된 내부 상태로 복귀하고 로컬 기록을 다시 읽는다.
- 세션 만료: manifest를 잃지 않고 재로그인 후 동일 request key로 재개한다.
- 텍스트 저장 실패: 사진 업로드를 시작하지 않고 입력과 로컬 원본을 유지한다.
- 사진 부분 실패: 성공 사진을 다시 올리지 않고 실패 item만 재시도한다.
- finalize 불일치: 부분 성공으로 표시하고 서버·로컬 개수를 함께 보여준다.
- 중복 요청: 기존 manifest와 후보를 돌려주며 새 레코드를 만들지 않는다.
- Storage 성공·DB 연결 실패: 미연결 객체를 cleanup queue에 기록하고 사용자에게 전체 성공으로 표시하지 않는다.
- 삭제 부분 실패: 남은 사진/DB 범위를 응답하고 재시도 가능 상태로 둔다.
- 배포 롤백: 가입 CTA를 로컬 안내 모드로 되돌리고, 기존 localStorage/IndexedDB 읽기를 계속 지원한다. 새 서버 데이터는 파괴하지 않는다.

## 15. 명세 자체검토
