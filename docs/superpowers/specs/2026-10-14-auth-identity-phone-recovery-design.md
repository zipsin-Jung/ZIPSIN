# 집신 로그인·회원가입·휴대폰 인증 통합 설계

- 작성일: 2026-10-14
- 상태: 서면 명세 사용자 검토 대기
- 기준 요구사항: `PSV1-AUTH-001~005`, `AUTHUX-001~006`
- 대체 예정 결정: `DEC-023`의 집신체크 SMS 생략 정책

## 1. 목표와 사용자 가치

집신체크로 유입된 사회초년생이 집신 계정을 만들 때 아이디 중복을 미리 확인하고 실제 휴대폰 번호를 인증한 뒤 어느 기기에서든 같은 계정으로 기록을 이어 보게 한다. 로그인 화면은 제공된 집신 기록 이미지를 사용해 제품 가치를 한눈에 설명하고, 계정을 잊은 사용자는 이메일 또는 인증된 휴대폰으로 안전하게 복구한다.

집신체크의 익명 로컬 사용은 계속 허용한다. 휴대폰 인증은 `집신 계정 생성·서버 저장`을 선택한 사용자에게만 필수다. 문자 OTP는 번호 소지 확인이며 공인중개사 자격, 집 소유권 또는 법적 본인확인을 뜻하지 않는다.

## 2. 확인된 현재 상태

- 집신과 집신체크는 같은 Next.js 앱, Supabase Auth와 사용자 ID를 사용한다.
- `account_usernames.username_normalized`에는 DB 고유 제약이 있지만 가입 전 중복확인 UI와 API는 없다.
- 일반 가입에는 `/signup/verify`가 있으나 실제 SMS 공급자는 비활성이고 개발·테스트용 mock만 있다.
- `/ck` 가입은 `DEC-023`에 따라 휴대폰 인증을 건너뛴다.
- 계정 복구는 가입 이메일로 보내는 비밀번호 재설정 링크만 지원한다.
- 비활성 OAuth 제공자는 버튼과 `연결 설정 후 사용할 수 있습니다` 문구가 함께 보인다.
- 로그인 왼쪽은 텍스트·기능 카드·집신이 캐릭터로 구성돼 있다.
- 사용자가 제공한 새 이미지 원본은 941×1672 PNG이며 가상의 집·기록·사진·일정 화면을 표현한다.

## 3. 승인 범위

### MVP

1. 로그인 데스크톱 왼쪽 영역을 사용자 제공 이미지로 교체한다.
2. 실제 활성화된 OAuth 버튼만 표시하고 미연결 안내문을 제거한다.
3. 회원가입 1단계에 서버 기반 아이디 중복확인을 추가한다.
4. 회원가입을 `1 집신과 함께 해요`와 `2 휴대폰 인증` 두 사용자 단계로 정리한다.
5. 집신체크 가입도 실제 휴대폰 인증 후 원래 `/ck`로 복귀한다.
6. SOLAPI로 실제 SMS 인증번호를 발송한다.
7. 계정 찾기에서 이메일 또는 인증된 휴대폰을 선택할 수 있게 한다.
8. 이메일 확인, 필수 동의, 역할 선택과 안전한 `next` 복귀를 보존한다.

### 제외

- 휴대폰 번호를 집·계약·사무소 접근 권한의 근거로 사용하지 않는다.
- PASS/NICE/KMC 법적 본인확인, 주민번호·주소 수집, 자동 계정 병합은 하지 않는다.
- 운영 Production 배포, 실제 비밀키의 Git 저장, 문자 마케팅 발송은 별도 승인 없이는 하지 않는다.
- 로그인·가입 외 전체 사이트의 브랜드 재설계는 하지 않는다.

## 4. 공급자 결정안

### 추천: SOLAPI 직접 연동

- 월 기본료와 API 사용료 없이 발송 건당 비용만 발생한다.
- 2026-10-14 공식 표준 단가는 단문 SMS 18원(VAT 별도)이다.
- API Key·API Secret과 활성 발신번호가 필요하다.
- 발신번호는 본인인증 또는 증빙서류 심사를 거쳐 등록한다.
- 서버 전용 `SolapiSmsTransport`가 문자 전송만 담당하고, OTP 생성·만료·시도 제한·검증·소비는 집신 DB가 담당한다.

Supabase 기본 Phone Auth는 Twilio·MessageBird·Vonage 중심이며 현재 집신의 아이디·이메일 계정에 번호를 추가하는 온보딩 구조를 크게 바꾼다. 이번 범위에서는 기존 계정과 DB 흐름을 유지하는 SOLAPI 어댑터가 더 작고 되돌리기 쉽다.

## 5. 요구사항과 수락기준

### AUTHUX-001 로그인 이미지와 OAuth 표시

- 데스크톱 로그인은 좌측 이미지, 우측 로그인 폼의 2열이다.
- 기존 좌측 대제목·기능 카드·집신이 캐릭터는 제거한다.
- 이미지는 `next/image`로 크기를 예약하고 핵심 집 모양이 잘리지 않게 표시한다.
- 1024px 미만에서는 로그인 폼이 먼저 나오고 이미지는 아래 보조 영역으로 이동한다. 390px 이하에서는 이미지를 숨겨 로그인 행동을 우선한다.
- 대체텍스트는 `집별 계약·사진·수리·일정 기록이 이어지는 집신 화면 예시`다.
- 실제 활성화된 OAuth 제공자만 표시한다. 0개면 소셜 영역과 구분선도 숨긴다.
- `연결 설정 후 사용할 수 있습니다` 문구는 표시하지 않는다.

### AUTHUX-002 아이디 중복확인

- 아이디는 영문 소문자·숫자·밑줄 4~20자이며 예약어를 사용할 수 없다.
- 형식이 맞을 때만 `중복 확인` 버튼이 활성화된다.
- 상태는 확인 전, 확인 중, 사용 가능, 이미 사용 중, 요청 제한, 서버 오류로 구분한다.
- 확인 성공 후 아이디를 바꾸면 즉시 확인 상태를 무효화한다.
- 중복확인 성공만으로 아이디를 예약하지 않는다. 최종 가입의 DB 고유 제약과 보상 삭제를 유지한다.
- 응답은 사용자 ID·이메일·계정 상태를 노출하지 않고 `no-store`로 제공한다.

### AUTHUX-003 두 단계 회원가입

- 진행표시는 정확히 `1 집신과 함께 해요`, `2 휴대폰 인증`이다.
- 1단계는 아이디 중복확인, 비밀번호·확인, 이메일, 필수 동의를 포함한다.
- 이메일 확인이 필요한 환경에서는 1단계 안의 `이메일 확인 대기` 상태로 표시한다.
- 2단계는 이름 확인, 휴대폰 번호, 인증번호, 선택 동의를 포함한다.
- 역할 선택은 가입 완료 뒤의 시작 설정이며 두 단계 진행표시에 포함하지 않는다.
- 집신체크 가입도 2단계를 완료하기 전에는 계정 저장 완료 또는 `/ck` 복귀로 표시하지 않는다.

### AUTHUX-004 실제 휴대폰 인증

- 인증번호는 암호학적 난수 6자리이며 유효시간은 5분이다.
- 동일 사용자·번호·요청 출처의 재발송은 최소 60초 간격으로 제한한다.
- 1시간·1일 발송량과 오답 최대 5회를 서버에서 제한한다.
- 새 코드를 발급하면 이전 코드는 즉시 무효다.
- 코드는 HMAC digest로만 저장하고 원문 번호·코드·API 비밀값을 로그에 남기지 않는다.
- 성공한 challenge는 가입 완료 트랜잭션에서 한 번만 소비한다.
- 공급자 장애·잔액 부족·발신번호 미승인·시간초과 시 인증을 우회하지 않고 복구 가능한 오류를 표시한다.
- production에서 mock 공급자를 선택하면 서버가 시작 또는 요청 단계에서 닫힌 상태로 실패한다.

### AUTHUX-005 이메일 또는 휴대폰 계정 찾기

- 진입 문구는 `아이디 찾기 · 비밀번호 재설정`이다.
- 사용자는 이메일 또는 휴대폰 탭을 선택한다.
- 이메일은 현재 Supabase 복구 링크 흐름을 사용한다.
- 휴대폰은 별도의 익명 recovery challenge를 발급하고 OTP 성공 뒤에만 아이디 확인과 비밀번호 재설정 세션으로 이동한다.
- 계정 존재 여부와 무관하게 최초 요청 응답 문구와 HTTP 상태는 동일하게 한다.
- 인증 성공 전에는 아이디·이메일·가입 여부를 표시하지 않는다.
- 복구 challenge와 재설정 세션은 만료·단일 사용·시도 제한을 적용한다.
- 전화번호 1개를 검증된 계정 1개에만 연결한다. 기존 중복 번호는 자동 삭제·병합하지 않고 배포 전에 감사한다.

### AUTHUX-006 접근성·반응형·복구

- 320px, 390px, 768px, 1440px와 200% 확대에서 가로 넘침이 없다.
- 모든 주요 조작은 44×44px 이상이고 키보드 포커스가 보인다.
- 상태는 색뿐 아니라 아이콘과 문장으로 전달한다.
- 입력 오류는 `aria-describedby`, 비동기 성공은 `aria-live=polite`, 오류 요약은 `role=alert`로 연결한다.
- 휴대폰 입력은 `autocomplete=tel`, 인증번호는 `autocomplete=one-time-code`와 숫자 키패드를 사용한다.
- 새로고침·뒤로가기·오류 후에도 안전한 입력과 원래 `next` 경로를 보존하되 비밀번호와 OTP를 URL·로그·분석에 남기지 않는다.

## 6. 화면 흐름

### 로그인

`/login → 활성 OAuth 또는 아이디 로그인 → 원래 next`

- 계정 찾기 링크: `아이디 찾기 · 비밀번호 재설정`
- 소셜 제공자가 없으면 아이디 로그인만 자연스럽게 표시한다.

### 아이디 회원가입

`/signup 1단계 → 이메일 확인 필요 시 확인 → /signup/verify 2단계 → /ck 또는 역할 선택`

- `/ck` 유입: 인증 완료 후 `/ck`로 복귀하고 로컬 기록을 유지한다.
- 일반 집신 유입: 인증 완료 후 역할 선택으로 이동한다.

### 계정 찾기

`/account-recovery → 이메일 또는 휴대폰 선택 → 중립 안내 → 검증된 채널 확인 → 아이디 확인·비밀번호 재설정`

## 7. 기술 설계

### 이미지

- 원본 저장 경로: `public/images/auth/zipsin-record-visual.png`
- 데스크톱: `fill`, `sizes`, `object-contain`을 기본으로 사용해 전체 구성을 보존한다.
- 모바일: 폼 뒤의 제한된 보조 영역 또는 390px 이하 숨김.

### 아이디 확인 API

- `POST /api/auth/username-availability`
- 입력: `{ username: string }`
- 출력: `{ status: 'available' | 'unavailable' | 'invalid' | 'rate_limited' | 'temporarily_unavailable' }`
- origin과 정규화 아이디의 HMAC rate limit을 적용한다.
- 가입 action은 이 응답을 신뢰하지 않고 현재 `account_usernames` unique 제약으로 다시 판정한다.

### OTP 저장·검증

- 기존 `phone_verification_states`를 additive migration으로 확장한다.
- 필드: `purpose`, `code_digest`, `attempts`, `provider_message_id`, `last_error_code`.
- `issue_phone_challenge`, `verify_phone_challenge`, 기존 `complete_signup`의 서버 전용 RPC 경계를 사용한다.
- `SolapiSmsTransport.sendOtp({ to, code, expiresInMinutes })`는 전송만 수행한다.

### 휴대폰 복구

- 가입용 상태와 분리된 `account_recovery_challenges`를 사용한다.
- 번호 원문은 필요한 최소 기간 동안 서버 전용으로 처리하고 공개 응답·클라이언트 로그에는 노출하지 않는다.
- 검증 완료 뒤 짧은 수명의 HttpOnly recovery 세션을 발급한다.
- 복구 세션에서만 `account_usernames` 조회와 Supabase 비밀번호 재설정 절차를 시작한다.

### 환경값

- `PHONE_VERIFICATION_PROVIDER=solapi`
- `SOLAPI_API_KEY`
- `SOLAPI_API_SECRET`
- `SOLAPI_SENDER_NUMBER`
- `PHONE_OTP_HMAC_SECRET`
- 모든 비밀값은 Vercel server-only 환경변수이며 Git과 `NEXT_PUBLIC_`에 넣지 않는다.

## 8. 개인정보와 운영 정책

- 휴대폰 번호 목적: 계정 보호, 가입 번호 확인, 사용자 요청 시 계정 복구.
- 문자 마케팅 동의와 인증문자 전송은 분리한다.
- OTP 원문은 저장하지 않는다.
- 인증번호·API 비밀값·전체 전화번호를 애플리케이션 로그에 남기지 않는다.
- SOLAPI 공식 API의 발송내역 보관기간과 집신 개인정보처리방침의 처리위탁·국외이전 여부를 배포 전에 고지한다.
- 전화번호 변경은 기존 로그인 세션 재인증과 새 번호 OTP를 요구한다. 번호 분실은 이메일 복구와 고객지원 수동 검토 경로를 남긴다.

## 9. 실패·복구와 롤백

- 공급자 장애 때 SMS 필수 가입을 조용히 우회하지 않는다.
- 인증 전 로컬 집신체크 기록은 삭제하지 않는다.
- 가입 최종 저장 실패 시 검증 상태와 안전한 입력을 유지하고 재시도를 제공한다.
- 새 테이블·필드는 additive migration으로 추가하고 사용자 데이터를 롤백 명목으로 삭제하지 않는다.
- 기능 플래그로 신규 SMS 발송과 휴대폰 복구 진입을 닫을 수 있게 하되, 서버의 필수 인증 가드는 클라이언트 플래그만으로 우회할 수 없게 한다.
- 공급자 준비 전에는 Preview에서만 UI와 mock 테스트를 검수하고 공개 Production에서는 진입을 열지 않는다.

## 10. 테스트와 완료 기준

- 아이디: 형식·예약어·중복·확인 후 변경·rate limit·DB 장애·동시 가입 경쟁.
- OTP: 실제 전송·오입력·만료·재사용·동시 발급·재전송 제한·시도 초과·공급자 장애·production mock 거부.
- 복구: 이메일/전화 존재·부재 동일 응답, 인증 전 정보 비노출, 토큰 만료·재사용·바꿔치기 거부.
- 경로: 아이디·Google·Kakao·집신체크 유입 모두 휴대폰 미인증 우회 불가, 인증 후 정확한 `next` 복귀.
- 화면: 이미지 실패 fallback, OAuth 0/일부/전체, 320·390·768·1440px, 200% 확대, 키보드·스크린리더 상태.
- 전체 unit·integration·Playwright·타입·Next.js production build와 커버리지 statements/branches/functions/lines 각각 80% 이상.
- Preview에서 실제 휴대폰 수신, 오답, 재발송, 만료와 실제 계정 복구를 검수한다.
- P0·P1 결함 0건이어야 G6 사용자 승인을 요청한다.
- 운영 배포는 별도 사용자 승인 전 수행하지 않는다.

## 12. 외부 준비와 승인 게이트

사용자가 준비하거나 직접 승인해야 하는 외부 항목은 다음뿐이다.

1. SOLAPI 계정 생성과 계정 인증
2. 문자에 표시할 발신번호 등록·활성화
3. 소액 충전 또는 자동충전 정책 결정
4. API Key·Secret을 Git이 아닌 Vercel 환경변수에 입력
5. 개인정보처리방침에 문자 처리위탁과 보유 기준 반영

이 다섯 항목이 준비되지 않아도 코드·DB·자동테스트와 Preview UI는 만들 수 있지만, 실제 휴대폰 수신과 운영 완료로 보고할 수 없다.
