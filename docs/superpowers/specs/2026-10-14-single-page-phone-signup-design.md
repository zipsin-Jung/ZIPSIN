# 집신 단일 화면 휴대폰 인증 회원가입 설계

- 작성일: 2026-10-14
- 상태: 사용자 승인
- 기준 요구사항: `SUA-AUTH-001~005`
- 관련 결정: `DEC-024`, `DEC-025`
- 대체 범위: 기존 명세의 `AUTHUX-003 두 단계 회원가입`

## 1. 목표

집신체크에서 유입된 사회초년생과 임차인이 별도의 휴대폰 인증 페이지를 찾지 않고 `/signup` 한 화면에서 회원가입을 끝내게 한다. 휴대폰 인증이 성공하기 전에는 Supabase Auth 사용자, 아이디, 프로필, 동의, 유입 기록을 만들지 않는다.

휴대폰 인증은 번호 소지 확인이며 법적 본인확인 또는 성인인증으로 표현하지 않는다. 집신체크의 익명 로컬 기록은 가입 성공 전후 모두 보존한다.

## 2. 확정 범위

### 포함

1. 비밀번호 신규가입을 `/signup` 한 화면으로 통합한다.
2. 입력 순서는 아이디·중복확인, 비밀번호·확인, 이메일, 휴대폰 번호·인증번호 받기, OTP·인증 확인, 필수동의, 회원가입 완료다.
3. 휴대폰 번호는 이메일 바로 아래에 배치하고, 발송 성공 후 OTP 입력을 바로 아래에 펼친다.
4. OTP 인증이 완료되고 최종 서버 검증을 통과한 뒤에만 계정을 만든다.
5. 이메일 확인이 필요한 환경에서는 같은 화면에 `이메일을 확인해 주세요` 종료 상태를 표시한다.
6. `/ck` 유입은 가입 성공 후 로컬 후보 기록을 유지한 채 `/ck`로 돌아간다.
7. 잔존한 `만 14세 이상` 동의·가드를 제거하고 약관·개인정보 필수동의만 한 번 받는다.

### 보존

- OAuth 신규가입과 기존 미완료 계정 복구에 필요한 `/signup/verify`와 로그인 사용자용 휴대폰 인증 경계는 유지한다.
- 로그인, 계정 찾기, 비밀번호 재설정, 기존 사용자 데이터 구조는 보존한다.

### 제외

- PASS·NICE·KMC 법적 본인확인, 주민번호·주소 수집
- 자동 계정 병합, 역할 선택 재설계, 전체 로그인 브랜드 개편
- 실제 비밀키의 Git 저장, 사용자 최종 승인 전 Production 배포

## 3. 요구사항과 수락기준

### SUA-AUTH-001 단일 화면 가입

- AC-001: 아이디 신규가입은 `/signup/verify`로 이동하지 않고 `/signup`에서 휴대폰 번호와 OTP를 연속 입력한다.
- AC-002: 휴대폰 번호는 이메일 바로 아래, `인증번호 받기`는 번호 입력 옆 또는 바로 아래, OTP와 `인증 확인`은 발송 후 그 아래에 표시한다.
- AC-003: 큰 2단계 진행표와 중복된 필수동의를 제거한다.
- AC-004: 320·390·768·1440px와 200% 확대에서 순서와 상태를 이해할 수 있고 주요 조작은 44px 이상이다.

### SUA-AUTH-002 계정 생성 전 휴대폰 인증

- AC-005: OTP 완료 전 Auth 사용자·아이디·프로필·동의·유입 영구 데이터는 0건이다.
- AC-006: OTP는 6자리, 5분 유효, 재발송 최소 60초, 오답 최대 5회이며 시간·일 발송 제한을 서버에서 적용한다.
- AC-007: 새 코드를 발급하면 이전 코드는 무효가 되고, 인증 후 번호를 바꾸면 인증 완료 상태도 즉시 무효가 된다.
- AC-008: 인증 증거는 같은 브라우저의 짧은 수명 HttpOnly 가입 세션과 서버 challenge에 묶고 최종 가입에서 한 번만 소비한다.
- AC-009: 전체 전화번호·OTP 원문·비밀번호·비밀키를 URL, 브라우저 저장소, 분석, 애플리케이션 로그에 남기지 않는다.

### SUA-AUTH-003 최종 가입

- AC-010: `회원가입 완료`는 아이디 확인, 비밀번호 규칙·일치, 이메일 형식, 휴대폰 인증, 필수동의가 모두 충족될 때만 활성화한다.
- AC-011: 최종 서버 action은 클라이언트 상태를 신뢰하지 않고 아이디, 이메일, 휴대폰 증거, 동의, 안전한 `next`를 다시 검증한다.
- AC-012: 이중 클릭·동시 요청에도 계정과 인증 증거는 정확히 한 번만 생성·소비한다.
- AC-013: 아이디·이메일·휴대폰 경쟁 충돌이나 DB 최종화 실패 시 불완전 계정을 남기지 않고 해당 항목에서 재시도하게 한다.
- AC-014: 성공 시 `/ck` 유입은 로컬 기록을 유지한 `/ck`, 일반 유입은 기존의 안전한 다음 경로로 이동한다.

### SUA-AUTH-004 상태·복구

- AC-015: 아이디는 확인 전·확인 중·사용 가능·중복·제한·오류 상태를 문장으로 표시하고 값 변경 시 확인을 무효화한다.
- AC-016: 문자는 전송 중·발송·재전송 대기·공급자 오류, OTP는 확인 중·성공·오답·만료·횟수 초과 상태를 해당 입력 아래에 표시한다.
- AC-017: 최종 가입은 처리 중·성공·이메일 확인 대기·충돌·서버 오류 상태를 표시하고 첫 오류 입력으로 초점을 이동한다.
- AC-018: 기존 미완료 계정은 새 계정을 만들지 않고 `가입을 이어서 완료해 주세요` 상태로 복구한다.
- AC-019: OAuth 신규가입과 기존 미완료 계정의 `/signup/verify` 흐름은 정상 작동한다.

### SUA-AUTH-005 개인정보·접근성

- AC-020: 전화번호 목적은 계정보호·가입번호 확인·사용자 요청 복구로 제한하고 마케팅 동의와 분리한다.
- AC-021: 필수 약관·개인정보 동의 원문 버전과 시점은 가입 성공 시에만 저장한다.
- AC-022: 입력은 label과 설명을 연결하고 비동기 상태는 `aria-live`, 오류는 `role=alert`로 알린다.
- AC-023: 휴대폰은 `autocomplete=tel`, OTP는 `autocomplete=one-time-code`와 숫자 키패드를 사용한다.
- AC-024: 휴대폰 인증을 법적 본인확인 또는 성인인증이라고 표시하지 않는다.

## 4. 사용자 흐름

### 신규 아이디 가입

`/signup → 아이디 중복확인 → 비밀번호·이메일 → 휴대폰 번호 → 문자 OTP 확인 → 필수동의 → 회원가입 완료 → 이메일 확인 대기 또는 안전한 next`

- 문자 발송 실패: 계정은 생기지 않고 같은 화면에서 재시도한다.
- OTP 오답·만료: 계정은 생기지 않고 오답 또는 재발송 안내를 표시한다.
- 번호 변경: 기존 성공 표시를 지우고 새 번호 인증을 요구한다.
- 최종 충돌: 계정을 중복 생성하지 않고 충돌한 입력으로 돌아간다.

### 기존 미완료·OAuth 가입

기존 사용자는 새 계정을 만들지 않고 현재 `/signup/verify` 또는 안전한 이어서 완료 상태를 사용한다. 신규 아이디 가입에서만 `/signup/verify`가 기본 경로에서 제외된다.

## 5. 기술 경계

### 익명 가입 의도

- 서버가 무작위 가입 의도를 만들고 `HttpOnly`, `Secure`, `SameSite=Lax`, 짧은 TTL 쿠키 `zipsin_signup_intent`로 같은 브라우저에 묶는다.
- 클라이언트는 OTP 원문 증거나 전화번호를 URL 또는 localStorage에 저장하지 않는다.

### API

- `POST /api/auth/signup/phone/send`
- `POST /api/auth/signup/phone/verify`
- 최종 Server Action `registerVerifiedPasswordAccountAction`

익명 API는 사용자 ID를 받지 않고 서버 쿠키의 가입 의도와 서버 challenge만 신뢰한다.

### 서버 전용 데이터

`anonymous_signup_phone_challenges`를 additive migration으로 추가한다. 최소 필드는 challenge ID, 가입 의도 digest, 전화번호, OTP digest, 시도 횟수, 발송·만료·검증·claim·소비 시점, 공급자 상태다.

- RLS를 활성화하고 anon·authenticated 직접 권한을 부여하지 않는다.
- OTP는 HMAC digest만 저장한다.
- 성공한 challenge의 불필요한 전화번호는 즉시 제거하고, 실패·만료 데이터는 최대 24시간 안에 정리한다.

### 원자 경계와 보상

최종 가입은 다음 순서를 사용한다.

1. 서버가 인증된 challenge를 짧게 claim한다.
2. Supabase Auth 사용자를 생성한다.
3. 서버 전용 RPC가 아이디, 프로필, 휴대폰 인증 시점, 동의, `/ck` 유입과 challenge 소비를 한 번에 최종화한다.
4. Auth 생성 뒤 최종화가 실패하면 이 요청이 만든 Auth 사용자를 즉시 삭제한다.
5. 즉시 삭제하지 못하면 cleanup queue에 기록하고 challenge를 재사용하지 못하게 격리한다.

아이디 중복확인은 예약이 아니며 최종 unique 제약을 다시 확인한다. 안전한 `next`는 기존 `sanitizeNextPath`를 유지한다.

## 6. 오류 문구 원칙

- 사용자가 고칠 수 있는 오류는 해당 입력 바로 아래에 쉬운 한국어로 표시한다.
- 공급자·설정 장애는 `현재 인증문자를 보낼 수 없습니다. 잠시 후 다시 시도해 주세요.`처럼 복구 행동을 안내한다.
- 아이디·이메일·휴대폰의 가입 존재 여부를 필요 이상으로 노출하지 않는다.
- 빨간 전역 오류만 띄운 채 원인을 알 수 없게 두지 않는다.

변경 제품 코드의 statements, branches, functions, lines는 각각 80% 이상 유지한다. 전체 테스트, 타입 검사, Next.js production build, 비밀정보 검사를 실행한다.

### Preview 실검수

1. Supabase migration·RPC와 service-role 환경값 확인
2. SOLAPI 발신번호·잔액·API 환경값 확인
3. 실제 휴대폰에서 정상 수신, 오답, 만료, 재발송, 공급자 오류 확인
4. OTP 전 Supabase Auth·제품 DB에 가입 데이터 0건 확인
5. 정상 가입 후 데이터 1건과 로그인·`/ck` 복귀 확인
6. 실패·이탈·동시 제출 뒤 고아 계정과 개인정보 잔존이 없는지 확인

빌드 성공은 브라우저 검수 성공으로 표현하지 않는다. P0·P1 결함 0건과 독립 품질 검수 통과 전에는 완료로 보고하지 않는다.

## 8. 외부 준비와 롤백

실문자 완료에는 Supabase migration, Vercel server-only 환경변수, SOLAPI API Key·Secret, 활성 발신번호와 잔액이 필요하다. 이 설정이 없으면 UI가 완성돼도 실제 가입 완료로 보고하지 않는다.

새 테이블·API는 additive로 추가한다. 운영 전 문제가 발견되면 이 기능 커밋을 되돌려 신규 비밀번호 가입 진입만 기존 2단계 흐름으로 복구하고, OAuth와 기존 사용자 데이터는 유지한다. 사용하지 않는 런타임 기능 플래그는 추가하지 않는다. Production 배포는 별도 사용자 승인 전 수행하지 않는다.

## 10. 승인 게이트

이 명세에서 사용자가 승인할 핵심은 다음 세 가지다.

1. `/signup` 한 화면에서 휴대폰 인증까지 완료한다.
2. OTP 인증 전에는 계정과 가입 데이터를 만들지 않는다.
3. 인증 증거를 서버에서 한 번만 소비한 뒤 계정을 만든다.

사용자는 2026-10-14 이 명세를 승인했다. 구현계획 검토 후 실패 테스트부터 진행한다.
