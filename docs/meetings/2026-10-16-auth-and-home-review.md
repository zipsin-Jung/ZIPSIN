- 범위: 2026-10-15~16 작업(로그인 시안, 회원가입 재디자인, 이메일 확인 제거, 아이디·비밀번호 찾기, 앱 받기 QR, 홈 상단 메뉴)

## 1. 한 줄 결론

화면과 코드는 거의 준비됐지만 **실제로 끝까지 눌러 본 증거가 아직 없다.** 데이터베이스가 코드보다 뒤처져 있어 가입 문자부터 막힐 가능성이 높고, "배포 직전"이라고 말하기에는 이르다.

## 2. 잘된 점

- 로그인·가입·찾기·새 비밀번호·완료 화면이 같은 가운데 카드 틀(AuthCard)로 통일됐다.
- 테스트 808 통과(2 skip), 커버리지 줄 92.9%·분기 83.3%, 빌드 성공, 390·1440px 확인.
- 개인정보 노출을 줄이는 장치: 아이디 일부 가림, 시도 횟수 제한, 오류 로그에 개인정보 미기록.
- 없는 기능을 있는 것처럼 보이지 않게 함: 약관 "보기" 링크 미생성, 수리·클린은 "준비 중" 안내.

## 3. 비판 — 문제와 위험

### 기획
1. **오늘 작업이 전부 "계정"에 몰렸다.** 첫 고객인 소규모 중개사무소의 핵심 흐름(집 등록·관계자 초대·수리 상태·전후 사진)은 진전이 없다.
2. **집신수리·집신클린을 메인 메뉴에 둔 것.** 제품 정의는 "수리 중개 플랫폼이 아니다"이다. 첫 결제 고객(중개사무소)에게 준비 중 메뉴 두 개는 "덜 만든 서비스"로 보일 수 있다.

### UX
3. **비밀번호 재설정에 이메일까지 요구하는 것이 오히려 막힘을 만든다.** 이메일은 확인하지 않고 받으므로, 가입 때 이메일을 틀리게 적은 사람은 아이디 찾기도, 비밀번호 재설정도 못 한다. 본인 확인의 실제 근거는 휴대폰 문자이고, 번호 하나에 계정 하나이므로 **이름 + 휴대폰 문자**만으로도 충분히 안전하다.
4. **가입 화면이 길다.** 이름·아이디(중복 확인)·비밀번호 2번·이메일·휴대폰 인증·동의 2개. 20~60대, 스마트폰이 익숙하지 않은 사용자 기준으로는 "중복 확인" 버튼을 따로 누르는 단계가 부담이다(입력이 끝나면 자동 확인 가능).
5. 가린 아이디(`zip***nt`)는 짧은 아이디일수록 기억에 도움이 덜 된다.
6. 휴대폰 홈 화면은 메뉴 줄이 추가돼 첫 화면 이야기 영역이 줄었다.

### UI
7. 초록색이 두 가지(인증 화면 #0B6655, 홈 #0b6b5d)로 섞여 있다. 큰 문제는 아니지만 디자인 기준을 하나로 정리해야 한다.

### 설계·개발
8. **데이터베이스 기록 관리가 없다.** Supabase에 "No migrations" — 업데이트를 손으로 넣어 왔고, 그래서 7개가 빠진 채 Preview가 돌아갔다. 실서비스에서도 같은 일이 생길 수 있다.
9. **실서비스 데이터베이스가 정해지지 않았다.** Supabase에는 `ZIPSIN Preview`(사용 중, "PRODUCTION" 표시)와 `ZIPSIN`(일시 중단) 두 개가 있다. zipsin.net이 어느 쪽을 쓸지 결정이 필요하다.
10. 이메일 미확인 예전 계정의 로그인 처리(비밀번호가 맞을 때만 확인 처리)는 Supabase 동작을 가정한 것으로, 실제 Preview에서 검증하지 않았다.
11. 화면에서 뺀 예전 이메일 재설정 코드가 남아 있다(지우지 않음, 나중에 정리 대상).

### 검수
12. **실제 문자 왕복, 가입 → 로그인 → 역할 선택 → 홈 흐름이 한 번도 실제로 검증되지 않았다.**
13. 여러 계정 권한(RLS) 검사 2건은 계속 skip — 통과로 세지 않는다.
14. 브라우저 자동 검사(Playwright e2e)를 오늘 돌리지 않았다.

### 시간선·과정
15. 시안 승인 → 코드 순서를 두 번 건너뛰었다(비밀번호 재설정에 아이디 추가, 이메일로 변경). 사용자 지시가 명확했지만 절차상 예외였다.
16. 같은 화면의 문구·흐름을 여러 번 오갔다. 질문을 묶어서 한 번에 정했다면 더 빨랐다.
17. 바탕화면 문서함 동기화를 하지 못했다(이 세션에서 컴퓨터 파일 연결이 없음). 기록은 GitHub에만 있다.
18. 솔라피 비밀키가 대화에 노출된 적이 있어 재발급이 필요하다.
