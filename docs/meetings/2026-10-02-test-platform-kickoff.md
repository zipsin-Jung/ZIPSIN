# 집신 테스트 플랫폼 4역할 킥오프 회의

- 날짜: 2026-10-02
- 목적: `/test` 테스트 플랫폼의 제작·검수·배포 순서 확정
- 상태: 회의 완료, 계획 사용자 승인 대기

## 총괄비서 결론

기존 `/` 랜딩페이지를 보존하고 실제 저장·접수가 없는 `/test` 클릭형 플랫폼을 별도로 만든다. 전체 TEST-001~016을 동시에 구현하지 않고, 첫 결제 고객인 공인중개사무소의 가치를 확인할 수 있는 T-01 사무소 업무 인수인계를 첫 수직 흐름으로 권장한다. 사용자 승인 전에는 개발과 배포를 시작하지 않는다.

## 기획·디자인 의견

- 순서는 기획 → 설계 → 테스트 설계 → 개발 → 검수 → 자동화 → 수정 → 완료보고 → 사용자 승인으로 한다.
- PRD, 유저플로우, UI 상태, 테스트 사이의 추적성을 유지한다.
- 네 역할은 대표 공인중개사·보조원·임대인·임차인을 기준으로 한다.
- 전 화면에 가상 데이터와 미전송 데모임을 알린다.
- 먼저 T-01을 검증하고 T-02, T-03으로 확장하는 것이 안전하다.

## 설계·개발 의견

- Next.js App Router의 `/test` 진입점과 기능별 컴포넌트 구조를 사용한다.
- 개인정보 없는 고정 가상 데이터와 명시적인 상태 로직을 사용한다.
- Vitest·Testing Library·Playwright를 도입하고 TEST ID를 테스트명과 추적표에 연결한다.
- 네 커버리지 지표를 각각 80% 이상으로 관리하되 대표 흐름 E2E를 별도로 통과시킨다.
- 스테이징 검수 뒤 사용자 승인을 받아 배포하고 직전 성공 배포를 롤백점으로 남긴다.

## 검수·비판 의견

- 정적 → 단위 → 통합 → 시나리오/E2E → 접근성·반응형 → 권한·개인정보 → 스트레스 → 회귀 순서로 검수한다.
- 권한 없는 직접 URL 접근, 이전 임차인 개인정보 노출, 중복 조작과 상태 불일치를 필수 실패 시나리오로 검사한다.
- 자동화 수치만으로 승인하지 않고 실제 브라우저 증거와 독립 판정을 함께 남긴다.
- P0·P1 결함 0건, 필수 시나리오 통과 후에도 상태는 사용자 승인 전까지 `승인 대기`다.

## 회의에서 확인된 미결정

- 첫 배포를 T-01 단독으로 할지 T-02까지 포함할지
- 공개 URL과 제한된 내부 테스트 중 배포 대상
- 커버리지 80%를 신규 테스트 플랫폼 코드에 우선 적용할지 저장소 전체에 즉시 적용할지

## 회의 결과

세 역할 모두 T-01 우선의 작은 완성 흐름, 구현 전 테스트 설계, 독립 브라우저 검수와 사용자 최종 승인을 권장했다. 상세 순서는 `docs/10-test-platform-delivery-plan.md`에 기록했다.
