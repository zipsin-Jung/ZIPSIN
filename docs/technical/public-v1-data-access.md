# 공개형 V1 계정 데이터와 접근 통제

## 데이터 등급

| 데이터 | 등급 | 저장·표시 원칙 |
|---|---|---|
| 사용자 UUID·주 역할 | 내부 | 본인 세션에서만 조회 |
| 이름·이메일 | 개인정보 | 본인만 조회·수정, 로그 제외 |
| 전화번호·인증 시각 | 중요 개인정보 | 번호 마스킹, 인증번호 저장 금지 |
| 동의 종류·버전·시각 | 준법 기록 | 본인 조회, 필수 이력 덮어쓰기 금지 |
| OAuth·SMS 비밀값 | 비밀정보 | 환경 비밀 저장소만 사용, DB·Git 금지 |

## 접근 원칙

- 네 테이블 모두 RLS를 활성화한다.
- `profiles`, `consent_acceptances`, `user_roles`는 `auth.uid() = user_id`인 본인만 읽을 수 있다. 민감한 쓰기는 검증된 `SECURITY DEFINER` RPC로만 수행한다.
- `phone_verification_states`는 본인이 결과만 읽을 수 있고 쓰기는 서버 전용 경로만 수행한다.
- 역할 선택은 집·사무소·계약 참여 레코드를 만들지 않는다.
- 서비스 관리자용 우회 정책은 이번 단계에 추가하지 않는다.

## 위협과 대응

- 타인 UUID 변조: RLS와 서버 세션 사용자 ID를 함께 검사한다.
- 전화 인증 결과 위조: 브라우저 쓰기 권한을 회수하고 공급자 검증 성공 후 서버만 기록한다.
- 동의 이력 덮어쓰기: 같은 문서 종류·버전은 처음 기록을 유지하고, 새 버전은 별도 행으로 보존한다.
- 비밀키 노출: 공개 환경변수에는 Supabase URL과 anon key만 허용한다.

## migration과 되돌림

첫 배포 전 빈 데이터베이스에 migration을 적용한다. 적용 실패 시 트랜잭션을 취소한다. 되돌려야 할 때는 신규 가입 진입을 먼저 끈 뒤, 데이터가 없는 Preview에서는 생성 역순으로 네 테이블을 삭제할 수 있다. 실제 사용자 데이터가 생긴 환경에서는 내보내기·행 수 검증·보존정책 확인 없이 테이블을 삭제하지 않는다.

## 감사 대상

이번 단계에서는 동의 버전과 시각을 보존한다. 집 초대, 참여 종료, 역할 권한 변경과 결제 상태 변경 감사는 해당 기능 단계에서 추가한다.

## 집·사무소 기록 접근 경계

- 주소나 집 ID만으로는 어떤 기록도 열 수 없다.
- 사무소 구성원은 개인 계정으로 접속하고, 활성 사무소 소속과 활성 집 담당 관계를 모두 확인한다.
- 대표 공인중개사는 사무소가 맡은 집을 볼 수 있고, 소속공인중개사와 보조원은 자신에게 배정된 집만 본다.
- 임대인·임차인·수리 참여자는 활성 `home_memberships` 관계가 있어야 집에 접근한다.
- `office_internal` 기록은 해당 사무소만, `current_contract` 기록은 그 계약 참여자와 담당 사무소만, `shared_history`는 현재 권한이 있는 참여자만 본다.
- 현재 임차인은 같은 주소의 이전 계약과 이전 임차인 정보를 볼 수 없다.
- 보조원은 사진 등록·일정 관리·단순 문서 정리는 할 수 있지만, 설명·조건 조율·계약 승인 권한은 갖지 않는다.
- 관계가 종료되면 사람의 접근 권한은 즉시 끝나고, 집과 사무소의 업무 기록은 삭제하지 않고 보존한다.

이번 migration은 로컬 코드에만 추가했다. Supabase Preview나 운영 DB에는 아직 적용하지 않았다.

## 유료 파일럿 후속 권한 강화 (2026-10-13, Task 1)

파일럿에는 `docs/superpowers/specs/2026-10-13-paid-pilot-predeployment-design.md`를 우선 적용한다. 위 공개형 V1의 장기 공용 이력·수리 참여자 방향을 보존하되, 이번 파일럿 조회·작성은 사무소 내부와 활성 현재 계약 공유 공간만 허용한다. `shared_history`와 수리 참여자 관계는 저장 구조를 보존하고 파일럿 접근에서는 제외한다.

- `202610130001_office_home_records.sql`은 보존한다. `202610130002_paid_pilot_core.sql`만 추가한다.
- 집·기록·첨부파일의 익명/인증 사용자 직접 쓰기 권한과 기존 쓰기 정책을 제거한다. 후속 단계가 원자 RPC를 연결하기 전까지 새 쓰기 경로는 제공하지 않는다.
- `homes.office_id`를 사무소 공간의 기준으로 삼고 담당·기록·초대의 집/사무소, 기록·참여·초대의 계약/집을 복합 외래키로 연결한다. 주소 일치로 병합하거나 권한을 부여하지 않는다.
- 대표는 해당 사무소의 모든 활성 집, 직원은 활성 소속과 활성 담당이 함께 있는 집만 조회한다. 시작 전·종료·만료 관계와 종료 계약은 접근을 허용하지 않는다.
- 기록 작성의 역할별 능력은 `canCreateRecord`로 표시하되 실제 관계는 DB `can_create_record`로 다시 검사한다. 계정의 주 역할 선택은 접근 권한이 아니다.
- 보조원은 사진·문서 정리·일정·할 일만 작성한다. 임대인·임차인은 현재 계약 공유 공간에 메모·사진·문서·수리 기록을 남기며 사무소 내부 할 일은 작성하지 않는다.
- 소속·담당·집 참여의 활성 행에만 고유 제약을 적용한다. 종료 행은 변경하지 않고 재초대/재배정 시 새 행을 만든다. 종료 시각은 필수이며 기존 관계의 사용자·범위·역할·시작 이력은 불변이다.
- 기록의 집·사무소·계약·공간·종류·작성자·작성시각·멱등성 키는 변경할 수 없다. 초대의 토큰 해시·범위·역할·만료·생성 이력과 사용/철회 결과도 되돌릴 수 없다.
- 오류는 허용된 공통 코드와 고정된 안내 문장으로 변환한다. DB 원문·제약 이름·주소·계약 내용을 사용자에게 반환하지 않는다.

### 적용 전 데이터 검토와 복구

외부 적용 전 백업과 행 수를 확인하고 기존 사무소 연결, 종료 시각, 초대 조합, 계약/집 조합, 중복 활성 관계를 검토한다. 하나의 집에 서로 다른 사무소 증거가 있으면 `ambiguous_home_office`로 전체 트랜잭션을 취소한다. 강화된 제약을 위반하는 기존 행이 있으면 적용을 취소하며 데이터를 자동 삭제하거나 임의로 정리하지 않는다. 사무소 증거가 없는 기존 집은 `office_id = NULL`로 보존하되 파일럿 접근에서 제외한다.

적용 실패는 트랜잭션 취소로 기존 권한·데이터·제약을 보존한다. 적용 성공 후 되돌릴 때는 쓰기 경로를 중단하고 백업과 신규 관계 이력을 확인한 뒤 수정 migration을 설계한다. 안전성이 약한 기존 직접 쓰기를 복구하거나 새 이력을 제거하는 자동 다운 migration은 제공하지 않는다.

이번 Task의 SQL 검증은 정적 불변조건 검사이며 실제 Postgres RLS·트리거·동시성 검증을 대신하지 않는다. 외부 DB 적용·6계정 검수는 승인된 후속 Task 8에 남긴다. 소속 종료와 담당 동시 종료·감사 이벤트, 초대의 원자 소비, 쓰기 RPC는 후속 Task 3~6에서 연결한다.

## 사무소 전체 집 접근 전환 (2026-10-13)

`DEC-016`과 `202610130004_office_wide_home_access.sql`을 이후 기준으로 사용한다.

- 활성 대표·소속공인중개사·중개보조원은 별도 담당 배정 없이 자기 사무소의 활성 집을 사용한다.
- 사무소 소속의 시작·활성·종료 상태를 매 요청에서 다시 확인한다.
- 임대인·임차인은 정확히 같은 현재 계약의 활성 관계로만 접근한다.
- `office_home_assignments`는 이력으로 보존하지만 신규 집 생성, 기록 생성, 조회, 업무 화면은 의존하지 않는다.
- 기존 배정 RPC의 인증 사용자 실행 권한을 회수하고, 예전 화면 경로는 집 상세로 되돌린다.
- 이 migration은 아직 Preview·Production DB에 적용하지 않았다. 실제 RLS 검증 전에는 배포 가능으로 판정하지 않는다.

## 집 관계자 초대와 종료 (2026-10-13)

`202610130005_relationship_invitations.sql`은 임대인·임차인·수리기사의 접근을 주소가 아니라 명시적 관계로 만든다.

- 임대인·임차인은 선택된 집의 활성 현재 계약과 정확히 일치할 때만 초대할 수 있다.
- 수리기사는 `repair_event` 범위와 최대 30일의 종료 시간이 반드시 필요하다.
- 초대 원문은 저장하지 않고 SHA-256 해시만 저장하며, 수락 시 행 잠금 후 한 번만 소비한다.
- 초대 미리보기는 사무소명·역할·범위·상태만 반환한다. 주소·연락처·계약 내용은 반환하지 않는다.
- 계약 종료·초대 만료·수리 참여 만료·명시적 관계 종료는 접근 거부 조건이다.
- 생성·수락·종료는 같은 트랜잭션의 감사 이벤트로 남긴다.
- 이 migration 역시 Preview·Production DB에 아직 적용하지 않았다. 현재 SQL 검사는 정적 불변조건 검증이며 실제 Postgres 동시성·RLS 검증은 외부 적용 후 별도로 수행한다.

## 공통 채팅 저장·읽음·알림 기반 (2026-10-13)

`202610130006_chat_core.sql`은 방 종류별 생성 규칙보다 먼저 공통 보안 경계를 만든다.

- `chat_rooms`, `chat_room_memberships`, `chat_messages`, `chat_read_states`, `notifications`는 모두 RLS를 사용한다.
- 메시지와 읽음 위치는 브라우저 직접 쓰기를 허용하지 않고 `send_chat_message`, `mark_chat_read` RPC만 사용한다.
- 발신자는 요청값이 아니라 `auth.uid()`로 결정하고, 활성 방·활성 참여를 매 요청에서 확인한다.
- `(방, 발신자, 멱등성 키)` 고유 제약과 원자 upsert로 재전송 중복을 막는다.
- 최근 메시지는 ID 역순 30개씩 불러오며 페이지와 실시간 결과는 ID 기준으로 중복 제거한다.
- 알림 테이블에는 메시지 본문이나 참여자의 개인정보를 저장하지 않는다.
- 실제 방 종류와 방 생성·초대 규칙은 후속 migration에서 추가한다.
- 이 migration은 Preview·Production DB에 아직 적용하지 않았다. 실제 RLS·동시 전송·읽음 경합 검증은 외부 적용 후 수행한다.

## 여섯 채팅방과 관계 재검사 (2026-10-13)

`202610130007_chat_room_types.sql`은 `direct`, `group`, `home_shared`, `office_internal`, `repair_event`, `support`만 허용한다.

- 개인·단체 초대 대상은 같은 사무소 또는 현재 집 관계가 있는 사용자로 제한하며 전체 사용자 검색 RPC는 만들지 않는다.
- 개인방은 정렬된 두 사용자 키, 사무소·계약·수리 기본방은 관계 키로 중복 생성을 막는다.
- 관계형 방은 활성 방 참여뿐 아니라 현재 사무소·계약·수리 관계를 매 접근마다 다시 확인한다.
- 수리방은 정확한 수리 참여자 한 명과 같은 현재 계약의 임대인·임차인만 포함하며 다른 수리기사에게 계약만으로 열리지 않는다.
- 단체방만 방장이 기존 관계자를 수동 초대할 수 있다. 나가기는 참여 이력을 삭제하지 않고 종료 시각을 남긴다.
- 집신 고객지원의 공식계정·운영자 감사는 후속 안전 migration에서 완성한다.

## 채팅 UI·첨부·실시간 복구 (2026-10-13)

- `/chats`와 `/chats/[roomId]`는 RLS로 조회 가능한 방과 메시지만 표시한다.
- 첨부 경로는 `chat/{room_id}/{message_id}/{attachment_id}`이고 비공개 `chat-attachments` 버킷만 사용한다.
- JPEG·PNG·HEIC·PDF, 파일당 20MB, 메시지당 최대 10개를 서버에서 다시 검사한다.
- 메시지 발신자만 자기 메시지에 첨부를 준비할 수 있고, 관계 종료 후에는 저장 경로를 알아도 읽을 수 없다.
- 준비 상태는 1시간 후 만료되며 부분 실패는 `failed`로 남겨 완료 파일처럼 노출하지 않는다.
- 파일 열람 URL은 권한 있는 `ready` 행 확인 후 300초만 발급한다.
- Realtime은 향상 기능이며 오류·오프라인·기능 플래그 비활성 시 Postgres 재조회로 복구한다.

## 채팅 안전과 공식 고객지원 (2026-10-13)

- `chat_blocks`는 개인방 양방향 접근 검사에 반영하고, `chat_reports`는 원문 본문 없이 메시지 ID·사유·신고자만 저장한다.
- `support_identities`의 고정 공식 신원만 공식 발신자로 사용할 수 있다.
- `support_authorizations`는 활성 대표 권한을 한 명으로 제한하며 해당 권한은 고객지원 방에만 적용된다.
- 공식 답변은 `sender_user_id`에 실제 답변자를, `sender_kind=support`와 `support_identity_id`에 표시 신원을 함께 남긴다.
- 일반 메시지 RPC로 공식 발신자를 지정할 수 없고 공식 답변 RPC는 활성 지원 권한을 다시 검사한다.
- 지원 대표 계정 UUID는 코드나 Git에 넣지 않는다. Preview 적용 시 승인된 계정 한 명을 별도 관리자 절차로 연결해야 한다.
- 사용자별 지원방은 `support:{user_id}` 관계 키로 하나만 만들고 답변 상태·알림 끄기를 별도 보존한다.
