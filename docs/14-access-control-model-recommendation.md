# 집신 권한 모델 권고안

- 작성일: 2026-10-08
- 상태: 권고안 · 사용자 승인 대기
- 연결 문서: `DEC-002`, `docs/meetings/2026-10-08-house-key-replanning-kickoff.md`

## 1. 오늘 조언의 핵심

집신을 `집 키를 나눠 주는 서비스`로 설명하면 하나의 열쇠가 집 전체 기록을 여는 것처럼 오해하기 쉽다. 집신이 실제로 풀어야 할 문제는 다음 질문이다.

> 누가, 어떤 관계로, 어느 집·계약·사무소의 어떤 자료에, 언제까지, 무엇을 할 수 있는가?

역할은 출발점일 뿐이다. `임대인`을 선택했다고 특정 집에 접근할 수 없고, `공인중개사`라고 모든 집을 볼 수 없으며, 초대받은 사람도 승인된 범위와 기간 안에서만 행동할 수 있어야 한다.

## 2. 용어를 쉽게 정리하면

| 용어 | 쉬운 뜻 | 집신 예시 |
|---|---|---|
| RBAC | 역할에 따라 기본 행동을 정함 | 대표는 직원 초대 가능, 보조원은 불가 |
| ABAC | 사람·자료·상황의 속성을 조건으로 판단 | 현재 계약이고 공유 만료 전일 때만 열람 |
| ReBAC | 사람과 대상 사이의 관계로 판단 | 이 사용자가 이 집의 현재 임차인인가 |
| 최소 권한 | 필요한 범위만 허용 | 배정 직원은 배정된 집만 열람 |
| 기본 거부 | 허용 근거가 없으면 차단 | 주소나 `home_id`를 알아도 접근 불가 |

코치님이 말한 `알벡`, `에이벡`은 각각 RBAC, ABAC를 가리킨 것으로 보인다. `딥다이`는 보통 `딥다이브(deep dive)`, 즉 한 주제를 깊이 파고드는 검토를 뜻한다.

## 3. AWS IAM에서 배울 원리

AWS IAM은 요청자를 인증한 뒤 요청 맥락을 만들고, 적용되는 정책을 평가해 허용 또는 거부한다. 중요한 원리는 다음과 같다.

1. 기본은 거부한다.
2. 허용 근거가 있어야 실행할 수 있다.
3. 명시적 거부는 허용보다 우선한다.
4. 사용자 쪽 정책과 자원 쪽 정책을 함께 볼 수 있다.
5. 권한 경계나 조직 정책 같은 상한선으로 이미 부여된 권한을 더 줄일 수 있다.
6. ABAC에서는 요청자 태그와 자원 태그가 맞는지 같은 조건을 사용할 수 있다.

AWS의 애플리케이션용 권한 서비스인 Verified Permissions는 `principal(누가)`, `action(무엇을)`, `resource(어디에)`, `context(어떤 상황에서)`를 기준으로 판단하며 RBAC와 ABAC를 함께 사용할 수 있다. Cedar 공식 설계 문서는 사용자와 자원의 관계에 기반한 ReBAC도 별도 패턴으로 설명한다.

집신이 배울 것은 AWS 제품 자체가 아니라 `인증과 권한 분리`, `자원 단위 판단`, `기본 거부`, `명시적 거부 우선`, `중앙화된 판정과 감사` 원리다.

## 4. 대안 비교

| 안 | 사용자 가치 | 개인정보·보안 | 개발·운영 부담 | 되돌리기 | 판단 |
|---|---|---|---|---|---|
| 현 상태: 화면별 조건문 | 초기에는 빠름 | 누락·불일치 위험이 큼 | 기능이 늘수록 급증 | 낮음 | 제외 |
| 순수 RBAC | 설명이 쉬움 | 같은 역할의 집별 차이를 처리하기 어려움 | 낮음 | 높음 | 보조 수단 |
| 순수 ABAC | 세밀함 | 규칙이 보이지 않고 속성 오류가 큰 권한으로 번질 수 있음 | 높음 | 중간 | MVP에 과함 |
| RBAC + ABAC | 역할과 조건을 함께 처리 | 집·계약 관계를 속성으로 억지 표현할 수 있음 | 중간~높음 | 중간 | 차선 |
| **RBAC + ReBAC + 제한적 ABAC** | 역할은 쉽고 집별 관계는 정확함 | 집·계약·사무소 경계를 명시 가능 | 중간 | 높음 | **권장** |

## 5. 권장 모델

### 5.1 RBAC: 사무소 안의 기본 직무

- 대표 공인중개사: 직원 초대·종료, 사무소 정책 관리, 담당 변경
- 보조원: 배정된 집의 업무·기록 처리
- 임대인: 연결된 집의 공유 승인·철회
- 임차인: 현재 계약 공간의 기록 작성·열람

역할은 가능한 행동의 최대 범위를 정할 뿐, 특정 집 접근을 자동으로 주지 않는다.

### 5.2 ReBAC: 실제 접근의 중심

사용자와 자원 사이에 다음 관계가 실제로 존재하는지 확인한다.

- `member_of(user, office)`
- `assigned_to(user, office_home_workspace)`
- `owner_of(user, home)` 또는 아직 공식 확인 전인 `accepted_landlord_invite`
- `tenant_of(user, active_contract)`
- `participant_in(user, case)`
- `shared_with(record, office|contract|user)`

`오너가 임대인을 초대한다`는 문장은 주체가 혼동될 수 있다. 초기 흐름은 `사무소가 임대인에게 집 연결 요청 → 임대인이 수락·공유 범위 승인`으로 표현하는 편이 안전하다. 임대인이 연결된 뒤에는 임차인이나 추가 사무소 초대의 승인 주체가 될 수 있다.

### 5.3 제한적 ABAC: 관계 위의 안전 조건

MVP에서는 검증 가능한 속성만 사용한다.

- 참여 상태: `active | pending | ended`
- 계약 상태: 현재 계약인지
- 공유 만료 시각
- 기록 공간: 사무소 내부, 임대인 공유, 현재 계약, 장기 집 이력
- 자료 민감도: 일반, 개인정보 포함, 계약 문서
- 요청 시점과 재인증 여부

위치, 기기 신뢰도, 위험 점수처럼 운영하기 어려운 속성은 후속으로 미룬다.

## 6. 권한 판정 문장

모든 서버 요청은 최소한 다음 질문으로 바꾼다.

```text
can(user, action, resource, context)?
```

예시:

```text
임차인 A가 사진 P를 볼 수 있는가?
= A가 P가 속한 현재 계약의 활성 참여자인가
AND P가 현재 계약 공유 공간에 있는가
AND 참여가 종료되지 않았는가
AND 명시적 차단이나 만료가 없는가
```

판정 우선순위는 다음과 같다.

```text
명시적 거부 또는 참여 종료 → 거부
테넌트·사무소 경계 불일치 → 거부
허용되는 역할 행동 아님 → 거부
대상과의 활성 관계 없음 → 거부
필수 조건 불충족 → 거부
나머지만 허용
```

## 7. 데이터와 구현 원칙

MVP는 별도 AWS 권한 서비스를 바로 도입하지 않고 기존 계획대로 Supabase Postgres와 Next.js 서버에서 시작한다.

- 역할: `office_memberships.role`
- 관계: `home_participants`, `contract_participants`, `case_participants`, `assignments`
- 상태·기간: 각 참여·공유 행의 `status`, `starts_at`, `ends_at`
- 자원 분리: 사무소 내부 원본과 승인 공유본을 별도 공간으로 구분
- 서버 판정: 공통 `can()` 계층에서 확인
- DB 방어선: Postgres RLS로 직접 조회도 차단
- 파일: 비공개 저장소와 짧게 만료되는 접근 주소
- 감사: 초대, 수락, 역할 변경, 담당 변경, 공유, 철회, 접근 종료 기록

화면에서 버튼을 숨기는 것은 편의 기능일 뿐 보안 수단이 아니다. 모든 읽기·쓰기·파일 발급에서 서버와 DB가 다시 판정해야 한다.

Amazon Verified Permissions나 Cedar 도입은 정책 수가 많아지고 여러 서비스가 같은 권한 결정을 공유해야 할 때 다시 검토한다. MVP부터 외부 정책 엔진을 넣으면 정책·데이터 동기화와 장애 대응 부담이 먼저 커진다.

## 8. 세 시간대 영향

### 지금

- `집 키` 대신 `집 연결 초대`, `공유 승인`, `접근 종료`라는 용어를 사용한다.
- 사무소 내부 공간과 임대인 승인 공간을 분리한다.
- 서버 공통 판정 함수와 RLS 테스트를 설계한다.

### 6개월 운영

- 직원 이동, 계약 종료, 초대 만료와 공유 철회가 반복되어도 같은 관계 모델로 처리할 수 있다.
- 권한 문의에 감사 기록으로 답할 수 있다.
- 정책 예외가 늘면 허용 규칙보다 `왜 거부·허용됐는지` 설명 도구가 필요해진다.

### 장기

- 매매, 공동소유, 법인·대리인, 여러 사무소 참여를 새로운 관계 유형으로 확장할 수 있다.
- 권한 엔진을 Cedar 같은 외부 정책 시스템으로 옮겨도 `누가-행동-자원-상황` 인터페이스는 유지할 수 있다.

## 9. 사전 부검

| 실패 가정 | 원인 | 조기 신호 | 대응 |
|---|---|---|---|
| 순수 RBAC로 갔다가 정보가 노출됨 | 같은 역할이면 모든 집을 본다고 처리 | `임대인인데 왜 이 집이 안/보이나요` 문의 | 집·계약 관계를 필수 조건으로 둠 |
| ABAC 규칙이 너무 복잡해짐 | 검증되지 않은 속성을 계속 추가 | 정책 예외와 수동 수정 증가 | MVP 속성을 상태·기간·공간으로 제한 |
| 관계가 끝났는데 파일 URL이 살아 있음 | 앱 권한과 저장소 권한 분리 실패 | 종료 계정의 파일 접근 로그 | 짧은 URL 만료, 철회, RLS·저장소 테스트 |
| 외부 권한 엔진이 개발을 늦춤 | 너무 이른 도입 | 정책 동기화 오류, 장애 시 전체 차단 | DB 기반으로 시작하고 이관 기준을 정함 |
| 사용자가 `키`를 전달 가능한 비밀번호로 이해 | 잘못된 용어 | 초대 링크 공유·재사용 문의 | 1회·만료·수락자 고정 초대와 쉬운 안내 |

## 10. 권고를 뒤집을 조건과 작은 실험

다음이 확인되면 권고를 재검토한다.

- 파일럿에서 집·계약 관계 없이 사무소 역할만으로 모든 업무가 충분하다면 ReBAC 범위를 줄인다.
- 고객마다 완전히 다른 권한 규칙을 직접 편집해야 한다면 정책 엔진 도입을 앞당긴다.
- 법률 검토에서 임대인 승인 전 사무소 내부 자료 보관 범위가 크게 제한되면 공간 구조와 MVP 범위를 바꾼다.

작은 실험은 실제 사무소 3곳의 대표·보조원에게 10개 행동의 권한표를 보여주고 `누가 볼 수 있는가`, `언제 끊겨야 하는가`, `예외가 무엇인가`를 확인하는 것이다. 코드 개발 전에 서로 다른 답변이 나온 항목만 정책 결정 대상으로 올린다.

## 11. 최종 권고

**권고:** 집신은 `RBAC를 기본 직무`, `ReBAC를 집·계약 접근의 중심`, `ABAC를 상태·기간·공간의 제한 조건`으로 사용하는 혼합 모델을 채택한다. 기본 거부와 명시적 거부 우선을 적용한다.

- 확신도: 높음
- 남은 위험: 소유권 확인 수준, 공동소유·법인·대리인, 계약 종료 후 열람 기간, 임대인 승인 전 자료 보관의 법적 범위
- 사용자 결정 필요: 이 모델을 제품 기준으로 승인할지 여부
