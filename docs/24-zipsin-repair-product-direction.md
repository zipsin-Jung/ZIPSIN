# 집신 수리 제품 방향

- 기준일: 2026-10-18
- 상태: G1 제품 방향·G2 UX 초안 — 사용자 승인 대기
- 구현 상태: 문서화만 완료, 실제 접수·저장·기사 초대·알림은 구현하지 않음

## 1. 한 문장 정의

집신 수리는 수리기사를 찾아주는 플랫폼이 아니라, `한 집에서 생긴 수리 요청을 관계자들이 함께 처리하고 그 결과를 집의 기록으로 남기는 기능`이다.

핵심 흐름은 다음과 같다.

> 요청 → 담당 확인 → 일정 조율 → 방문·처리 → 완료 확인 → 개인정보를 제외한 집 이력 보존

공인중개사무소에는 반복 연락·누락·인수인계를 줄이는 업무 도구가 되고, 임차인과 임대인에게는 진행 상황과 결과를 함께 확인하는 창구가 된다.

## 2. 확인된 기준과 가정

### 확인된 기준

- 집신은 계약·입주·거주·수리·퇴거 기록을 집 한 채에 연결하는 서비스다.
- 공인중개사무소는 초기 결제 고객이자 도입 채널이다.
- 수리는 여러 집 사건 중 하나이며 기사 매칭·견적·결제가 제품 중심이 아니다.
- 주소, 역할 선택, 전화번호만으로 기록 접근 권한을 주지 않는다.
- 집 이력은 이어질 수 있지만 이전 계약자의 이름·연락처·대화·계약정보는 자동으로 이어지지 않는다.
- 현재 제품에는 실제 수리 접수·저장·기사 초대·알림이 구현되어 있지 않다.

### 검증이 필요한 가정

- 사무소가 가장 먼저 비용을 낼 이유는 기사 탐색보다 반복 연락, 상태 확인, 증빙 누락과 직원 인수인계 감소에 있다.
- 요청 과정에서 기록이 자연스럽게 쌓이면 별도 사후 입력보다 반복 사용률이 높다.
- 이미 알고 있는 수리기사를 사건 단위로 초대하는 것만으로도 첫 가치를 검증할 수 있다.

## 3. 역할별 가치

| 역할 | 현재 문제 | 집신 수리의 가치 |
|---|---|---|
| 대표 공인중개사 | 멈춘 수리와 담당자를 한눈에 알기 어렵다 | 답변 대기·기한 초과·오늘 방문과 담당자를 확인한다 |
| 보조원·소속공인중개사 | 전화·메신저·사진을 다시 정리하고 인수인계한다 | 다음 행동과 최근 기록을 사건에서 이어간다 |
| 임대인 | 현장에 가지 않으면 증상·일정·결과·영수증을 알기 어렵다 | 허용된 범위에서 진행과 완료 결과를 확인한다 |
| 임차인 | 같은 사진과 설명을 반복해서 보내고 진행 상황을 묻는다 | 한 번 요청하고 현재 상태와 다음 일정을 확인한다 |
| 수리기사 | 필요한 증상·방문 정보가 여러 연락에 흩어진다 | 지정된 사건의 필요한 자료만 보고 작업 기록을 남긴다 |

## 4. 권장 MVP

첫 구현은 `임차인 요청 → 사무소 확인·조율 → 기존 기사 제한 초대 → 전후 기록 → 요청자 완료 확인` 한 흐름으로 제한한다.

### 포함

- 활성 관계가 있는 집에서 수리 사건 생성
- 장소·증상·설명·사진과 연락 선호 시간 기록
- 담당자·다음 행동·기한 지정
- 방문 일정 제안·확인·변경·취소
- 사건별 대화, 수리 전·중·후 사진과 문서
- 처리자 작업 완료와 요청자·관리자 완료 확인 분리
- 처리 내용·교체 설비·영수증 선택 요약
- 개인정보를 제거한 항목만 장기 집 이력으로 선택 전환
- 기사에게 특정 사건·필요 자료·유효기간만 허용하는 초대
- 여러 집 업무 홈의 답변 대기·기한 초과·오늘 방문 표시

### 후속

- 반복 수리와 설비 교체 주기
- 외부 기사 참여 링크 개선
- 선택 기록 PDF 내보내기
- 알림 채널 확대
- 사용자가 확인하는 AI 분류·요약 제안

### 제외

- 기사 자동 매칭·추천·광고·평점
- 견적 비교·입찰, 결제·정산·송금
- 품질 보증·분쟁·책임 판정
- AI 하자·안전 진단과 OCR 자동 확정
- 보험 청구, 긴급 출동 약속과 전화 녹취
- 주소만으로 과거 집 이력 열람

## 5. 요구사항과 수락기준 초안

| ID | 요구사항 | 핵심 수락기준 |
|---|---|---|
| ZR-001 | 권한 있는 현재 관계자가 집에서 수리 사건을 만든다 | 초안 저장, 제출 필수값 안내, 중복 제출 방지, 저장 실패 뒤 입력 복구를 제공한다 |
| ZR-002 | 대표·담당자가 담당자, 다음 행동과 기한을 지정한다 | 활성 사건마다 현재 담당·다음 행동·예정일 또는 미정 사유가 보이고 변경 이력이 남는다 |
| ZR-003 | 참여자가 방문 일정을 제안하고 확인한다 | 상대가 확인하기 전에는 확정으로 표시하지 않고 변경자와 이전 일정을 남긴다 |
| ZR-004 | 참여자가 허용된 범위에서 대화·사진·문서를 남긴다 | 업로드 실패를 재시도할 수 있고 채팅 사진은 동의 없이 장기 이력에 편입되지 않는다 |
| ZR-005 | 역할별 허용 행동으로 상태를 변경한다 | 처리자의 작업 완료는 `완료 확인 요청`이며 권한 있는 확인자가 확인해야 `완료`가 된다 |
| ZR-006 | 완료 때 처리 결과를 요약한다 | 장기 이력 전환 전 개인정보와 공개 범위를 확인하고 이전 계약자 연락처·대화는 전환하지 않는다 |
| ZR-007 | 수리기사는 지정 사건을 정해진 기간만 본다 | 초대 만료·관계 종료 즉시 읽기·쓰기·파일 접근을 차단하며 주소만으로 접근할 수 없다 |
| ZR-008 | 여러 집 담당자는 우선 처리할 사건을 본다 | 답변 대기·기한 초과·오늘 방문을 구분하고 사건마다 가장 중요한 다음 행동 1개를 표시한다 |

## 6. 상태와 화면 초안

### 사건 상태

`확인 필요 → 조율 중 → 방문 예정 → 처리 중 → 완료 확인 요청 → 완료`

별도 상태로 `보류`, `취소`, `재확인 요청`을 둔다. 자동 완료는 정책 승인 전 사용하지 않는다.

### 화면

1. `SCREEN-ZR-01 집 홈`: 지금 할 일 최대 3개, 활성 수리 사건, 수리 요청
2. `SCREEN-ZR-02 요청 작성`: 장소·증상·설명·사진·공개 대상 확인
3. `SCREEN-ZR-03 사건 상세`: 상태·담당·다음 행동·예정일, 일정·대화·기록 시간선
4. `SCREEN-ZR-04 방문 일정`: 제안·확인 대기·확정·변경·취소
5. `SCREEN-ZR-05 완료 확인`: 전후 비교, 처리 내용, 영수증, 완료 확인·추가 확인 요청
6. `SCREEN-ZR-06 전체 수리 업무`: 오늘 방문·답변 대기·기한 초과·최근 변경
7. `SCREEN-ZR-07 참여자와 접근`: 열람 범위·만료일·초대 취소·접근 종료
8. `SCREEN-ZR-08 완료 기록`: 현재 계약 기록과 개인정보 제거 장기 집 이력 분리

필수 화면 상태는 빈 상태, 초안, 제출 중, 성공, 업로드 실패·재시도, 담당 미지정, 답변 대기, 일정 충돌, 권한 거부, 초대 만료, 관계 종료, 보류, 취소, 완료 확인 대기, 완료와 재확인 요청이다.

## 7. 접근 권한 원칙

`전체 액세스`는 모든 사람이 모든 기록을 보는 권한으로 해석하지 않는다. 제품 전체 기능을 설계하되 실제 접근은 사건 중심 최소 권한으로 제한한다.

- 대표·담당 직원: 참여 중인 사무소·집·사건과 사무소 내부 기록
- 임대인: 연결된 집과 허용된 수리 사건
- 임차인: 현재 계약과 자신이 참여한 사건
- 수리기사: 초대받은 사건의 필요한 사진·일정·대화만, 자동 만료 필수
- 기본 비공개: 계약서 원본, 계좌정보, 다른 사건, 사무소 내부 메모, 불필요한 연락처
- 장기 집 이력: 설비·위치·작업 종류·완료일·승인된 사진 등 비개인 정보만 선택 전환

화면에서 버튼을 숨기는 것만으로 권한을 보호하지 않고, 실제 구현 단계에서는 서버 인가와 파일 접근 정책을 함께 검증한다.

## 8. 가장 작은 검증 실험

4주 동안 소수 사무소의 실제 수리 사건으로 `수리 사건 보드`를 검증한다. 아래 수치는 성과 실적이 아니라 실험 제안값이다.

- 대상: 사무소 3곳, 실제 사건 10~20건
- 기능: 요청, 집 연결, 담당자, 5단계 진행, 전후 사진, 영수증 선택 첨부, 역할별 공개, 기간 제한 기사 참여
- 측정: 담당 확인 시간, 일정 확정 시간, 사건당 확인 연락 수, 사진·영수증 누락, 인수인계 질문, 완료율, 반복 사용과 실제 지불 의사
- 계속 기준: 참여 사무소 다수가 반복 사용하고 절반 이상 사건이 완료까지 집신 안에서 갱신되며 반복 연락 또는 누락 감소의 현장 증거가 있다
- 수정 기준: 대부분 사후 입력만 하거나 이중 입력이 늘고 기사·임차인 참여가 가입·권한 때문에 막힌다

## 9. 선택지와 권고

| 선택지 | 장점 | 큰 위험 | 판단 |
|---|---|---|---|
| 기록 협업형 | 집 이력이 쌓이고 다른 집 사건으로 확장하기 쉽다 | 별도 기록 업무로 느껴질 수 있다 | 결과 보존 구조로 채택 |
| 접수·진행 관리형 | 반복 연락·누락·인수인계를 바로 줄일 수 있다 | 상태·알림·권한 설계가 필요하다 | 첫 진입점으로 권고 |
| 기사 매칭 플랫폼형 | 성공 시 거래 수익 가능 | 공급자 모집·품질·분쟁·결제 운영, 브랜드 왜곡 | 현재 제외 |
| 소개만 유지 | 구현 부담이 없다 | 실제 사용·지불 학습이 없다 | 실험보다 열위 |

통합 권고는 `접수·진행 관리를 진입점으로 삼고 결과는 집의 장기 기록으로 남기는 방향`이다. 실제 데이터에서 가장 큰 문제가 기사 탐색으로 반복 확인되고 공급자·거래 빈도·분쟁 운영 능력과 지불 증거가 생길 때만 매칭을 별도 재검토한다.

## 10. 구현 전 사용자 결정

- 누가 사건을 만들고 누구에게 즉시 알려야 하는가
- 임대인과 사무소 중 누가 비용·일정·최종 완료를 확인하는가
- 비용과 영수증의 입력·열람 범위는 어디까지인가
- 수리기사 초대 기본 유효기간과 신원 확인 수준은 무엇인가
- 계약 종료 뒤 임차인의 사건 열람 기간은 얼마인가
- 어떤 완료 결과를 누가 장기 집 이력으로 전환할 수 있는가
- 사진·대화·영수증 보존기간과 삭제 요청 처리 주체는 누구인가

이 결정들은 접근·개인정보·책임 의미를 바꾸므로 G1 승인 후 G3 기술 설계 전에 확정한다.

## 11. 승인 게이트와 다음 행동

- G1 제품기획: 본 방향, ZR-001~008, MVP·제외 범위 승인
- G2 UX·UI: FLOW/SCREEN/STATE와 실제 문구·복구 방식 승인
- G3 아키텍처: 데이터·서버 인가·파일·보존·감사 이력 승인
- G4 테스트 설계: 정상·실패·권한·경계 TEST-ID 승인
- G5 구현·검수: 자동검사와 실제 브라우저·권한 검수
- G6 사용자 승인: 검수 통과 뒤 Preview 확인 및 최종 승인

현재 다음 행동은 사용자의 G1 방향 승인이다. 승인 전에는 실제 접수 기능 구현이나 배포를 시작하지 않는다.
