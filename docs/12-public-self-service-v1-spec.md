# 집신 공개형 서비스 V1 제품 명세

- 작성일: 2026-10-02
- 상태: 설계안 작성 완료 · 사용자 검토 대기
- 기준 결정: `DEC-008`, `DEC-010`
- 구현 방식: 기존 Next.js App Router 프로젝트 확장

## 1. 목표

누구나 집신에 가입해 자신의 역할을 선택하고, 첫 집과 기록을 만들고, 일정과 사진을 확인한 뒤 요금제의 테스트 결제까지 경험할 수 있는 하나의 완전한 흐름을 만든다.

첫 구현의 완료 흐름은 다음과 같다.

`간편가입 → 휴대전화 인증 → 필수 동의 → 역할 선택 → 첫 집 등록 → 기록 작성 → 캘린더 확인 → 테스트 결제`

## 2. 사용자별 해결할 문제

| 역할 | 첫 버전에서 해결할 문제 | 첫 성공 행동 |
|---|---|---|
| 대표 공인중개사 | 사무소 업무와 집 기록이 개인 직원에게 흩어짐 | 사무소를 만들고 첫 집을 등록한다 |
| 보조원 | 배정받은 집과 다음 일을 한곳에서 보기 어려움 | 초대로 참여해 집 기록과 일정을 확인한다 |
| 임대인 | 여러 집의 상태·사진·일정을 반복 확인해야 함 | 본인 집을 만들거나 초대를 수락해 기록을 남긴다 |
| 임차인 | 입주 상태와 집에서 생긴 일을 증거와 함께 남기기 어려움 | 초대를 수락해 현재 계약 공간에 기록을 남긴다 |

역할 선택만으로 사무소·집·계약 기록 접근 권한을 부여하지 않는다. 권한은 생성, 확인된 초대 또는 별도 검증을 통해 얻는다.

## 3. 접근 방식 비교와 결정

| 안 | 설명 | 장점 | 위험 |
|---|---|---|---|
| A. 세로 흐름 완성 | 가입부터 첫 집·기록·일정·테스트 결제까지 한 줄을 완성 | 실제 사용 가능 여부를 빠르게 검증 | 첫 범위의 기능 수를 엄격히 제한해야 함 |
| B. 화면 우선 | 전체 화면을 먼저 만든 뒤 서버를 연결 | 시각 결과가 빠름 | 화면과 데이터·권한 구조를 다시 만들 가능성이 큼 |
| C. 전체 기능 동시 개발 | 채팅·AI·PDF·결제까지 한 번에 구현 | 기능 목록은 풍부함 | 일정, 개인정보, 권한과 품질 위험이 너무 큼 |

**결정:** A안을 사용한다. 첫 버전 밖의 기능을 섞지 않고 한 사용자 흐름을 실제로 동작하게 만든다.

## 5. 요구사항

### PSV1-AUTH-001 간편가입

- 역할: 모든 방문자
- 트리거: `시작하기` 또는 `로그인` 선택
- 사전조건: 로그아웃 상태
- 기본 흐름: Google·카카오·네이버 중 하나 선택 → 제공자 인증 → 집신 가입 절차 복귀
- 상태: 초기, 제공자 이동 중, 성공, 취소, 제공자 오류, 이미 연결된 계정
- 개인정보: 제공자 식별자와 제공받은 이름·이메일만 임시 처리한다.
- 수용 기준:
  - 세 제공자 버튼이 구분되고 키보드로 동작한다.
  - 취소·오류 시 다시 시도할 수 있으며 가입 완료로 표시하지 않는다.
  - 같은 이메일만을 근거로 서로 다른 소셜 계정을 자동 병합하지 않는다.

### PSV1-AUTH-002 휴대전화 인증과 가입 완료

- 역할: 소셜 인증을 마친 사용자
- 트리거: 집신 가입 절차 복귀
- 사전조건: 유효한 소셜 인증 결과
- 기본 흐름: 전화번호 입력 → 인증번호 확인 → 이름·이메일 확인 → 필수 동의 → 가입 완료
- 상태: 입력, 전송 중, 인증번호 대기, 시간 만료, 횟수 제한, 불일치, 성공, 서버 오류
- 개인정보: 전화번호 원문은 로그에 남기지 않고 표시할 때 마스킹한다.
- 수용 기준:
  - 인증 성공 전에는 가입 완료가 불가능하다.
  - 필수 동의와 문자·이메일 마케팅 선택 동의를 분리한다.
  - 동의 문서 버전과 동의 시각을 저장한다.
  - 만 14세 미만은 가입을 완료할 수 없다.

### PSV1-ROLE-001 역할 선택

- 역할: 가입 완료 사용자
- 트리거: 최초 로그인
- 사전조건: 인증된 계정
- 기본 흐름: 대표 공인중개사·보조원·임대인·임차인 중 주 역할 선택 → 역할별 설명 확인 → 계속
- 상태: 미선택, 선택, 저장 중, 성공, 오류
- 개인정보·권한: 역할 선택은 업무 기록 접근 권한이 아니다.
- 수용 기준:
  - 역할별로 가능한 일과 추가 확인이 필요한 일을 평이한 문장으로 보여준다.
  - 보조원과 임차인은 초대 없이 타인의 사무소·집을 볼 수 없다.

### PSV1-HOME-001 첫 집 만들기 또는 초대 참여

- 역할: 대표 공인중개사, 임대인, 초대받은 보조원·임차인
- 트리거: 빈 홈 화면의 기본 행동 선택
- 사전조건: 로그인과 역할 선택 완료
- 기본 흐름: 집 만들기 또는 초대 코드·링크 확인 → 필요한 최소 정보 입력 → 집 홈 표시
- 상태: 빈 화면, 입력, 중복 후보, 확인 대기, 성공, 오류, 권한 부족, 종료된 초대
- 개인정보: 정확한 주소는 권한 있는 참여자에게만 보이고 검색 공개 정보로 사용하지 않는다.
- 수용 기준:
  - 주소만으로 기존 비공개 기록에 연결되지 않는다.
  - 빈 화면에는 `첫 집 등록` 또는 `초대 확인` 중 역할에 맞는 한 가지 기본 행동을 강조한다.
  - 중복 후보는 자동 병합하지 않고 확인 흐름으로 보낸다.

### PSV1-REC-001 집 기록 작성과 확인

- 역할: 해당 집의 활성 참여자
- 트리거: 집 홈에서 `새 기록`
- 사전조건: 집 접근 권한
- 기본 흐름: 기록 종류·제목·내용 입력 → 선택적으로 사진·일정 연결 → 저장 → 타임라인 표시
- 상태: 빈 목록, 입력, 업로드 중, 저장 중, 성공, 오류, 권한 부족, 참여 종료
- 개인정보: 기록은 집·현재 계약·함께 처리하는 일 중 선택된 안전한 공간에 저장한다.
- 수용 기준:
  - 작성자, 작성 시각, 집, 기록 공간을 함께 저장한다.
  - 저장 실패 시 입력 내용을 유지하고 재시도할 수 있다.
  - 참여가 종료된 사용자는 새 기록을 쓰지 못한다.

### PSV1-PHOTO-001 사진 첨부와 다시 보기

- 역할: 기록 작성 권한이 있는 사용자
- 트리거: 기록 작성 또는 상세에서 사진 선택
- 사전조건: 허용된 파일 형식·크기
- 기본 흐름: 사진 선택 → 미리보기 → 업로드 → 기록 연결 → 사진 모아보기에서 재확인
- 상태: 선택 전, 미리보기, 업로드 중, 성공, 형식 오류, 용량 오류, 네트워크 오류
- 개인정보: 원본 저장 위치는 비공개이며 권한 확인된 임시 주소로만 제공한다.
- 수용 기준:
  - 업로드 실패 사진과 성공 사진을 구분한다.
  - 사진은 연결된 집과 기록에서 다시 볼 수 있다.
  - 파일명만으로 공개 접근 가능한 주소를 만들지 않는다.

### PSV1-CAL-001 집 일정

- 역할: 해당 집의 활성 참여자
- 트리거: 기록에서 일정 추가 또는 캘린더의 `일정 추가`
- 사전조건: 집 접근 권한
- 기본 흐름: 집·제목·시작 시각 입력 → 저장 → 월간 캘린더와 집 기록에 표시
- 상태: 빈 달, 일정 있음, 입력, 저장 중, 성공, 오류, 권한 부족
- 개인정보: 일정 상세는 해당 집의 권한 있는 참여자만 본다.
- 수용 기준:
  - 월 이동과 오늘 이동이 가능하다.
  - 일정에서 연결된 집·기록으로 이동할 수 있다.
  - 시간대는 Asia/Seoul을 기본으로 저장·표시한다.

### PSV1-PAY-001 테스트 요금제 결제

- 역할: 가입 완료 사용자
- 트리거: 유료 요금제의 `테스트로 선택`
- 사전조건: 로그인, 테스트 결제 모드
- 기본 흐름: 요금제 확인 → 토스 테스트 결제창 → 성공·취소·실패 복귀 → 테스트 구독 상태 표시
- 상태: 요금제 선택, 결제 준비, 결제창, 검증 중, 테스트 성공, 취소, 실패, 중복 요청
- 결제·보안: 클라이언트 성공 URL만으로 완료 처리하지 않고 서버에서 금액·주문·상태를 검증한다.
- 수용 기준:
  - 모든 화면에 실제 청구가 없는 테스트임을 표시한다.
  - 성공 요청을 재전송해도 중복 구독이 생기지 않는다.
  - 실제 결제 키와 실결제 전환 스위치는 운영 코드·Git에 저장하지 않는다.

### PSV1-ACCOUNT-001 계정 설정과 탈퇴 요청

- 역할: 로그인 사용자
- 트리거: 프로필의 `계정 설정`
- 사전조건: 로그인
- 기본 흐름: 프로필·동의 내역 확인 → 선택 동의 변경 또는 탈퇴 요청
- 상태: 정상, 저장 중, 성공, 재인증 필요, 오류
- 개인정보: 탈퇴와 법적 보관 대상의 구분은 정책 확정 전 임의로 약속하지 않는다.
- 수용 기준:
  - 마케팅 동의는 필수 동의와 독립적으로 변경된다.
  - 탈퇴 요청 전 데이터 영향과 처리 상태를 설명한다.

## 7. 데이터·권한 설계 원칙

> 2026-10-08 검토 메모: 세부 권한 모델은 `docs/14-access-control-model-recommendation.md`와 `DEC-013`의 사용자 승인 후 확정한다. 현재 권고는 RBAC로 역할의 기본 행동을 정하고, ReBAC로 사무소·집·계약·사건 관계를 확인하며, ABAC는 상태·기간·기록 공간의 제한 조건으로만 사용하는 방식이다.

- 계정, 프로필, 역할, 집, 계약 참여, 기록, 사진, 일정, 동의, 테스트 주문을 분리한다.
- 모든 집·기록·사진·일정 조회는 서버에서 참여 권한을 확인한다.
- 장기 집 이력과 계약별 개인정보 공간을 구분한다.
- 이전 계약자의 이름·연락처·대화·개인자료는 다음 계약 조회에서 제외한다.
- 사진은 비공개 저장소를 사용하고 짧은 만료시간의 접근 주소를 발급한다.
- 감사 대상 행위는 초대, 권한 변경, 참여 종료, 결제 상태 변경으로 제한해 기록한다.

## 8. 기술 방향

- 프런트·서버: Next.js App Router의 서버 런타임
- 데이터·인증·파일: Supabase Auth, Postgres, Storage
- 소셜 제공자: Google, Kakao, Naver
- 휴대전화 인증: 공급자 어댑터를 먼저 정의하고 업체 확정 후 연결
- 테스트 결제: 토스페이먼츠 테스트 환경
- 배포: Vercel Preview와 Production 분리
- 비밀값: Vercel 환경 변수와 각 서비스 비밀 저장소 사용

기존 정적 내보내기는 서버 인증·권한 확인을 위해 제거하되, 기존 랜딩페이지의 주소와 콘텐츠는 유지한다.

## 9. 테스트와 품질 기준

- 테스트 주도 순서: 실패 테스트 → 최소 구현 → 통과 → 리팩터링
- 단위·통합: Vitest, React Testing Library, user-event
- 브라우저 시나리오: Playwright
- 접근성: 자동 검사와 수동 키보드 확인
- 커버리지: Lines, Statements, Functions, Branches 각각 80% 이상
- 권한·계약 개인정보 분리·결제 금액 검증은 커버리지와 별개로 필수 사례 100% 통과
- P0·P1 결함 0건이어야 배포 승인 요청 가능
- 빌드 성공과 실제 브라우저 검수 성공을 별도로 기록

## 10. 대표 검증 사례

### 사례 A: 임대인의 첫 기록

임대인이 Google로 가입하고 휴대전화를 인증한 뒤 역할을 선택한다. 첫 집을 등록하고 입주 전 사진 기록과 다음 방문 일정을 저장한다. 사진 모아보기와 캘린더에서 같은 자료를 다시 확인한다.

### 사례 B: 초대받지 않은 임차인

임차인이 가입하고 주소를 검색한다. 같은 주소가 있어도 기존 기록은 보이지 않는다. 유효한 초대를 받은 뒤에만 현재 계약 공간을 볼 수 있다.

### 사례 C: 테스트 결제 재시도

사용자가 BASIC 테스트 결제를 취소한 뒤 다시 시도한다. 취소는 구독으로 표시되지 않고, 성공 콜백이 중복 도착해도 하나의 테스트 구독만 생성된다.

## 12. 구현 전 확정이 필요한 외부 항목

## 13. 배포 단계와 되돌림

1. 로컬 테스트 환경: 가상 계정과 토스 테스트 결제
2. Preview: 테스트 사용자만 접근, 실제 개인정보 최소화
3. Production 준비: 도메인·약관·운영정보·모니터링 확인
4. 공개 가입: 인증 제공자와 개인정보 절차가 준비된 뒤 활성화
5. 실결제: 사업자 등록과 PG·카드사 승인이 끝난 뒤 별도 승인으로 활성화

권한 누출, 개인정보 노출, 결제 금액 불일치 또는 핵심 흐름 중단이 확인되면 신규 가입·결제 진입을 즉시 끄고 직전 성공 배포로 복귀한다.
